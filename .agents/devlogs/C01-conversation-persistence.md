## Session 1 — 2026-08-10

### What I asked for / what came back
- `chat_messages` gains `question_id` (FK → `questions`, RESTRICT like every other FK in F02)
  and `action` (new `ConductorAction` Postgres enum), plus an `(interview_id, created_at)`
  index. `questions` gains `widget JSONB` and `intent TEXT`.
- Hand-written migration `20260810120000_conductor_conversation`, following the F02 protocol:
  every column nullable, no backfill, readable by the code that predates it.
- `GET /state` gains `messages[]`, built by a new `resolveMessages`. `transcript` is untouched.

### Methodology trace
- Brainstormed the shape with the ledger owner before any code: the argument that settled it is
  in ADR-C01 — once an interviewer decides *when* to advance, the conversation is the state, and
  §3.8 requires a refreshed room to rebuild from `GET /state` alone.
- Six read-only agents mapped the surfaces first (interview module, `packages/ai`, speech,
  frontend room, report pipeline, test/run infra). That map is what kept the migration to two
  tables — the abandoned sweeper's `chat_messages` dependency and the report's
  question/answer-pair transcript would both have been easy to break blind.

### Friction — the ordering trap
- `created_at` alone is not a total order here. A user utterance and the interviewer's reply to
  it are written inside one request and can land on the same millisecond; a replay that puts the
  answer before the question is a *different interview*, and the conductor then reasons about
  it. Every read of the conversation orders by `created_at` **then `id`**, in `conductor.ts` and
  in `state.ts` both, and both say why.
- Second-guessed `action` as a plain text column. Made it a Postgres enum to match F02's rule
  that membership is enforced by the database — and because `continue` needs to be a *value*:
  "stayed on this question deliberately" and "nothing was recorded" are different facts.

### What I rejected and rewrote by hand
- First draft put the conversation in Redis keyed by interview. Rejected: the report is
  generated by a worker in another process, possibly hours later, and Redis in this system holds
  only fan-out and rate-limit state. Losing the key would lose the interview.
- First draft of `resolveMessages` returned the rows verbatim, leaking `trace_id` to the client.
  Rewrote to map explicitly — `trace_id` joins a K6 log line to a row and is nobody's business
  in a browser.
