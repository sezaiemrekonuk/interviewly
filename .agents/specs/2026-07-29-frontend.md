## Scope

This spec pins the Next.js `web` app: the route map and per-screen composition (§4.3 — landing,
the auth family including verification and reset (K8.6), the three onboarding cards (§3.3), the
Jotform-shaped setup screen, pre-join, the interview room, report, history and admin), the
first-run routing rule (K8.7), the specified loading/empty/error states and the 390 px variants of
setup and room, the server-state data layer
(React Query, no Redux — K11), the SSE nudge-then-refetch client (K11), the question-widget
renderer (§3.9), the text-mode room behaviour including the client-driven avatar state
machine and typed-question animation (§3.8), the admin Recharts surface bound to K11's fixed
metric definitions, and internationalisation — `next-intl`, English default with Turkish
selectable, and the error-code→locale-string mapping that keeps the API free of display
strings (§4.5). It is the section `ui` reads to know which screens and components exist, and
the section `backend` reads to know how its endpoints and codes are consumed. MVP is
**text mode only** (§12); the voice room is out of scope here.

**Not in this spec** (named owner):

- Design tokens, colour, typography, spacing, motion values (§4.2); the Cambly/Jotform
  visual references (§4.1); the accessibility floor (§4.4). — `ui`. This spec composes
  screens and behaviour; `ui` owns the visual language they are dressed in. Frontend
  **honours** §4.4 (keyboard nav, focus ring, `aria-live` transcript, `alt`,
  `prefers-reduced-motion`); it does not re-decide it.
- The `AvatarState` enum and the five static images per persona, the asset pipeline, the
  content-addressed keys and public-read caching (§3.6). — `ui`/`db`. Frontend consumes
  `personas.avatar_set` keys and drives *which* state shows in text mode (§3.8); the enum
  and the images are `ui`.
- Every HTTP endpoint, the session cookie, the room-state shape, all error **codes**, rate
  limits, ownership/authorisation, CSRF — `backend`. Frontend consumes them verbatim and
  never re-decides a shape or a code.
- The error-code **registry file** and the shared TS types package — foundations F-a
  (`F01`, §4.5, §5.2). Frontend imports the codes and owns only the *locale messages* keyed
  by them.
- `ReportPayload`/`Scores`/`Question` **schemas** and their content — `ai`/`db` (K15, K4).
  Frontend renders them; it does not validate or produce them.
- The voice interview room: live ASR transcript, mic-level bar, self-camera tile, the
  `AmplitudeAvatarDriver`, ElevenLabs WSS connection (§3.2, §3.5, §3.6). — `voice`,
  authored last (§12). The room *layout* is shared (§3.8) and defined here for text mode;
  voice-only controls are `voice`.
- CSP, the edge, `/assets/*` routing, `next/font` self-hosting mechanics (§7.4, §4.2,
  K14). — `infra`/`ui`. Frontend relies on same-origin `/api`, `/events`, `/assets` and
  writes no absolute origins (§11.3).

## Contracts

The surface frontend exposes to `ui` (what to style) and the way it consumes `backend`
(what to satisfy).

### Route map (Next.js App Router)

| Route | Screen (§4.3) | Ground | Auth | Primary data source |
|---|---|---|---|---|
| `/` | Landing (1) | gradient | public | none — static |
| `/register` | Register (2) | gradient | public | `POST /auth/register`, `GET /auth/google` |
| `/sign-in` | Sign in (3) | gradient | public | `POST /auth/login`, `GET /auth/google` |
| `/verify-email` | Verification pending (4) | gradient | required | `POST /auth/verify-email/request` |
| `/verify-email/[token]` | Verification confirm (4) | gradient | public | `POST /auth/verify-email/confirm` |
| `/forgot-password` | Reset request (5) | gradient | public | `POST /auth/password-reset/request` |
| `/reset-password/[token]` | Reset confirm (5) | gradient | public | `POST /auth/password-reset/confirm` |
| `/onboarding/[step]` | Onboarding cards 1–3 (6–8) | gradient | required | `GET /me/profile`, `PATCH /me/profile`, `POST /me/profile/complete`, `POST /uploads` (`kind=cv`) |
| `/interviews/new` | Setup (9) | gradient | required | `POST /uploads`, `POST /interviews`, `POST /interviews/:id/profile` |
| `/interviews/:id/pre-join` | Pre-join device check (10) | gradient | required, owner | `GET /interviews/:id/state` (+ `getUserMedia`, client only) |
| `/interviews/:id/room` | Interview room (11) | flat | required, owner | `GET /interviews/:id/state`, `POST /interviews/:id/answers`, SSE |
| `/interviews/:id` | Report + transcript (12, US-21) | flat | required, owner | `GET /interviews/:id` |
| `/dashboard` | History list (13, US-22) | flat | required | `GET /me/interviews` |
| `/admin` | Admin list + stats (14) | flat | required, `role=admin` | `GET /admin/interviews`, `/admin/stats` |
| `/admin/interviews/:id` | Per-call cost detail (US-26) | admin | admin | `GET /admin/interviews/:id` |

Server components fetch through `INTERNAL_API_URL` during SSR; the browser fetches
same-origin `/api/*` on `PUBLIC_ORIGIN` (§9.3, §11.3). No route hardcodes an origin.

**Ground** is the `ui` gradient/flat assignment (§4.2, closed list) — the client does not choose
it per screen; it follows this column.

### First-run routing (K8.7)

After **any** successful sign-in (password, Google, or a just-completed registration) the client
routes on the `GET /me` fields, in this order:

| Condition | Destination |
|---|---|
| `onboardingCompletedAt` is null | `/onboarding/[first unfilled step]` |
| Onboarding done, `interviewCount === 0` | `/interviews/new` |
| Otherwise | `/dashboard` |

The decision inputs come from the server (`GET /me` returns `onboardingCompletedAt`,
`emailVerifiedAt`, `interviewCount`) so two screens can never disagree about where a user
belongs. **The dashboard is not removed** — the reference direction's "no dashboard" applies to
*first run only*; history list/view/delete is a mandatory requirement (K8.7).

An unverified user is **not** blocked here: `/verify-email` is a prompt the user can leave, and
enforcement (if `EMAIL_VERIFICATION_REQUIRED` is on) surfaces as `EMAIL_NOT_VERIFIED` on
`POST /interviews`, handled in the error table below.

### Data layer — React Query (K11)

Almost all state is **server state**; there is no Redux. Real client state (locale, the
in-room lifecycle phase, which text is mid-animation) is `useState`/context only.

- **Query keys** are stable and endpoint-shaped:
  `['me']`, `['me','profile']`, `['me','interviews', {cursor}]`, `['interview', id, 'state']`,
  `['interview', id]`, `['admin','interviews', filters]`, `['admin','stats', filters]`.
- **`['interview', id, 'state']` is the single source of room truth.** Every SSE nudge and
  every reconnect invalidates exactly this key; the component always renders from the
  refetched response, never from an SSE payload (K11).
- List endpoints are **cursor-paginated** (`nextCursor`); the client never assumes a page
  count (§8.1 — pagination mandatory).
- Mutations (`answers`, `profile`, `register`, `login`, `delete`) invalidate the affected
  query keys on success; on a `409`/state error they invalidate `['interview', id, 'state']`
  and let the refetch resolve the truth rather than reconciling optimistically.

### SSE client (K11)

- One `EventSource` per open room on `GET /events/interviews/:id`. Events are `{ type }`
  only; **the payload is ignored beyond its arrival**.
- On **any** event → invalidate `['interview', id, 'state']`. On `error`/disconnect → the
  browser's native `EventSource` reconnect runs; on `open` → one invalidation to catch
  anything missed while disconnected. There is no `Last-Event-ID`, no ordering assumption,
  no replay handling — the refetch is idempotent (K11, §11.2).
- Resume-after-refresh (US-19) needs no special path: mounting the room fetches
  `['interview', id, 'state']`, which already carries `currentIndex`, `mode`, `persona`
  and `transcriptCursor`.

### Error-code → UI behaviour (§4.5)

The API returns `{ error: { code } }`, **never a display string**. Frontend maps **every**
registry code to a localized message via `next-intl` key `errors.<CODE>`, and a small set of
codes additionally route:

| Code(s) | UI behaviour |
|---|---|
| `UNAUTHENTICATED` | Redirect to `/sign-in`, preserve the return path |
| `FORBIDDEN` | Redirect to `/dashboard`; admin routes render a not-authorized state |
| `INTERVIEW_NOT_FOUND` | Render a not-found screen (existence not leaked — matches backend `404`) |
| `QUESTION_NOT_CURRENT`, `INVALID_STATE_TRANSITION` | Silent `['interview', id, 'state']` refetch; no error toast (the nudge pattern already self-heals) |
| `BUDGET_EXCEEDED` | Refetch state; the interview is now `evaluating` → route to the report wait (US-21) |
| `RATE_LIMITED`, `DAILY_INTERVIEW_LIMIT` | Inline localized message with the retryable context |
| `EMAIL_NOT_VERIFIED` | Route to `/verify-email` with the attempted action preserved; the setup form's state is not lost |
| `EMAIL_TOKEN_INVALID`, `EMAIL_TOKEN_EXPIRED` | Render the failure inline on the verify/reset screen with a **request a new link** action — never a bare toast on a dead-end page |
| `EMAIL_RESEND_COOLDOWN` | Keep the resend button disabled and show the remaining seconds; the countdown is authoritative from the response, not from a local timer alone |
| any other registry code | Inline/toast `errors.<CODE>`; an **unknown** code falls back to `errors.UNKNOWN` and is never rendered raw |

Frontend introduces **no new error codes** — it is a pure consumer of the registry.

### i18n message contract (§4.5)

- `next-intl`, locale in a cookie, **English default, Turkish selectable**. Keys authored in
  English first; `messages/en.json` is the source, `messages/tr.json` mirrors its keys.
- Namespaces: `errors.*` (one key per registry code + `UNKNOWN`), plus per-screen namespaces
  (`landing.*`, `auth.*`, `verify.*`, `reset.*`, `onboarding.*`, `setup.*`, `prejoin.*`, `room.*`,
  `report.*`, `dashboard.*`, `admin.*`) and `mascot.*` for the pose `alt` strings (§4.2.1).
- LLM-generated content (questions, report text, transcript) is **content, not UI** — it is
  rendered in the interview language (§3.4), never routed through `next-intl`, and never
  interpreted as HTML (see [Security](#security)).

### Question-widget render contract (§3.9)

A question carries `kind` and, when `kind = 'widget'`, a widget descriptor in the room-state
`currentQuestion.widget` field. The client renders the matching widget, and on submit
serializes the user's choice into the `POST /interviews/:id/answers` body as
`{ questionId, transcript, inputMode: 'widget' }` — the same body shape as a typed answer,
with the selection encoded in `transcript`. The descriptor is a discriminated object
`currentQuestion.widget = { kind: 'mcq' | 'ordering' | 'code', options?: string[], language?:
string }`; the answer serializes to a deterministic readable line — the chosen option text
(`mcq`), the ordered option list (`ordering`), or the code verbatim (`code`). This shape is
pinned jointly with the `backend` spec's room-state contract.

### Admin charts (K11)

Recharts, bound to `GET /admin/stats`. The client **renders** the numbers backend computed
to K11's fixed definitions (`averageDurationMs`, `completed`/`unfinished`, `totalTokens`,
`perOccupation[]`, `weakestQuestions[]`); it never recomputes a metric client-side, so two
screens can never disagree (K11).

## Behaviour

Numbers, not adjectives. Two implementers reading this produce the same client.

### 1. Landing (§4.3 screen 1)

One screen: a large heading (56 px step), one subline, a single primary CTA, a three-step visual
explanation, `wave` mascot. No long marketing page. The CTA routes to `/register` for a new
visitor and `/sign-in` otherwise (no anonymous flow — K8, §15.2). Landing LCP target **< 2.5 s**,
initial JS bundle **< 250 KB gzip** (§8.1); it renders as a server component with no client data
fetch, and preloads **only** the `wave` pose (§4.2.1).

### 1a. Auth screens (§4.3 screens 2–5, K8.6)

| Screen | Composition | States |
|---|---|---|
| `/register` | email + password + **Continue with Google**, inline validation, link to `/sign-in`, `wave` mascot | **loading:** submit button in-flight, fields locked. **error:** `errors.PASSWORD_TOO_SHORT` / `errors.EMAIL_TAKEN` inline **on the field**, not as a toast. **empty:** n/a |
| `/sign-in` | mirror of register + **Forgot password?** link | inline `errors.INVALID_CREDENTIALS`; `errors.ADMIN_MUST_USE_PASSWORD` renders inline on the Google button, since that is the control that failed |
| `/verify-email` | `think` mascot, "check your inbox", what happens next, **Resend** with a live countdown, and an explicit "continue without verifying" link when `EMAIL_VERIFICATION_REQUIRED` is off | **loading:** resend in-flight. **error:** `errors.EMAIL_RESEND_COOLDOWN` keeps the button disabled and shows remaining seconds. **empty:** n/a |
| `/verify-email/[token]` | confirm-on-mount, then success → first-run routing | **loading:** "verifying…". **error:** `EMAIL_TOKEN_INVALID` / `EMAIL_TOKEN_EXPIRED` with a **request a new link** action |
| `/forgot-password` | one email field | success message is **identical whether or not the account exists** (K8.6 — no enumeration); the client must not branch its copy on the response |
| `/reset-password/[token]` | new password + confirm, ≥ 10 chars | on success: "you have been signed out everywhere" + route to `/sign-in`, because the reset revoked every session (K8.6) |

Password strength feedback is a **length indicator only** (≥ 10 characters), matching the single
server rule (K8.5). A client-side complexity meter would invent a requirement the API does not
enforce.

### 1b. Onboarding cards (§4.3 screens 6–8, §3.3 layer 1)

`/onboarding/[step]` with `step ∈ {1,2,3}`, one centred card at a time on the gradient ground.

| Step | Fields | Mascot |
|---|---|---|
| 1 | full name, current job title, date of birth | `point` |
| 2 | education rows (school, degree, field, graduation year), **+ Add another**, max **5** rows | `think` |
| 3 | hobby chips (multi-select) + free-text interests, **Upload CV** (optional) | `cheer` |

- **Progress is `1/3 · 2/3 · 3/3`**, Continue and Back, and **Skip for now** on every card.
- **Each card persists on Continue** via `PATCH /me/profile` with only that card's fields — not
  on finish. `['me','profile']` is invalidated on success.
- **Resume is derived from the server profile, not from local storage**: mounting
  `/onboarding/[step]` reads `GET /me/profile`; the first-unfilled-step redirect uses that
  response, so closing the browser on card 2 resumes on card 2 (§3.3).
- Deep-linking to a later step than the profile supports redirects back to the first unfilled
  step; the client never renders a step whose predecessors are unknown.
- **Skip** and **Continue on the last card** both call `POST /me/profile/complete`, then run
  first-run routing. A skipped profile is partial data, never an error state.
- **CV upload** posts to `POST /uploads` with `kind=cv`; the client shows the filename and a
  **Replace** action, mirrors the backend limits (≤ 10 MB, PDF) for a fast rejection, and renders
  `PDF_TEXT_TOO_SHORT` as "we couldn't read this PDF — you can still continue", because the CV is
  optional and must never become a wall.
- **The date-of-birth field carries a one-line note that it is not sent to the interviewer AI**
  (§3.3). We collect it, so we say what we do with it.

### 2. Setup (§4.3 screen 9, §3.1, §3.7)

`/interviews/new`, modelled on Jotform's "Describe your form" (§4.1): **one big listing textarea**
carries the screen; everything else is secondary to it. `point` mascot on the left, heading and
subline centred above the input.

**Input footer actions** (inside the input's container, secondary weight): **Upload listing PDF**,
**Upload CV**, **Talk** (sets `mode = 'voice'`). **Primary action: Go on.**

**Suggestion chips** below the input prefill the textarea client-side (common occupations, "paste
a job listing"); they issue no request. **Three option cards** along the bottom edge:
*Start from scratch* (clears and focuses the box), *Use my CV* (prefills the pre-questions from
`['me','profile']`), *Try a sample listing* (loads the seeded sample). Practice mode, a template
library and URL import are **not present** (§4.3.1) — no disabled buttons for cut features.

Then, still on this route:

1. **Listing** — paste text **or** upload a PDF (`POST /uploads`, then `POST /interviews`
   with the `uploadId`). Client-side pre-checks mirror backend limits (≤ 10 MB, PDF) for a
   fast rejection but the server is authoritative; `PDF_TEXT_TOO_SHORT` prompts the user to
   paste instead (US-04).
2. **Detected summary, editable** (US-05, §15.2 story 3) — the `POST /interviews` response's
   `occupation`, `occupationCluster`, `language` and the `hrQuestionCount`/`techQuestionCount`
   split are shown as `Backend Developer · Turkish · 3 HR + 5 technical`; occupation and
   language are editable and re-submittable before commit. The count is chosen here and its
   split is displayed before the user commits (§3.7).
3. **Pre-questions** (§3.3 layer 2) — a 2–3 field form (years of experience, areas of interest,
   target seniority) posted to `POST /interviews/:id/profile`, **or** an explicit *Skip* that
   posts `{ skip: true }`. Skipping is a first-class choice, not an abandoned form. The server
   merges these with the account profile and the CV text into `candidate_profile` (§3.3) — the
   client sends only this layer and never assembles the merge itself.

**States for this screen** (§4.3): **loading** — `Go on` in-flight, textarea locked, no spinner
over the whole page; **empty** — first visit with an untouched box, where the chips and option
cards are the only content that matters; **error** — `LISTING_REQUIRED`, `UPLOAD_*`,
`DAILY_INTERVIEW_LIMIT` and `EMAIL_NOT_VERIFIED` all render **against the input or its footer
action**, never as a page-level failure that loses typed text. Typed listing text survives every
error on this screen.

- **Voice mode routes to `/interviews/:id/pre-join`; text mode goes straight to the room.**
- The **avatar sets for both personas are preloaded** during the waiting beat so the room
  opens with no pop-in (§3.6, cited). The "waiting for the host to accept your join request"
  beat covers the HR batch generation (< 8 s, §3.7/§8.1); the client shows it until
  `GET /interviews/:id/state` reports `state = 'hr_round'` with a live `currentQuestion`.

### 2a. Pre-join (§4.3 screen 10) — voice mode only

Camera preview bound to a local `<video>` (never uploaded — §3.2), mic level bar, the
permission prompt, camera toggle **off by default**, and the "nothing is recorded, video never
leaves your browser" note. A **Join** action opens the room with exactly the device state chosen.
Permission denied → the screen offers **continue in text**, which is the same downgrade path as a
mid-interview voice failure (§3.8, `voice`). Text-mode interviews never reach this route; a direct
visit redirects to the room.

### 2b. Mobile variants (§4.3, 390 px)

Both mobile layouts are specified because a naïve reflow breaks them:

- **Setup:** mascot shrinks to a small inline figure above the heading; the textarea is full-width
  and at least 40% of viewport height; footer actions become an icon row; suggestion chips scroll
  horizontally in one row; the three option cards stack full-width **below** the primary action.
  `Go on` is sticky to the bottom edge.
- **Room:** only the **active** persona tile is full-size; the other persona and the self-camera
  collapse into a horizontal strip above it; the question banner stays pinned under the header;
  the transcript becomes a bottom sheet (collapsed by default, drag/tap to open); the control bar
  is fixed to the bottom edge and does **not** auto-fade (a fading control bar on touch is a trap).

### 3. Text-mode interview room (§3.8) — MVP

The same room layout for both modes (§4.3); this section defines the **text** path. Its
whole state is `['interview', id, 'state']`; the client holds only presentation lifecycle.

**Screen composition** (§3.2, §3.8) — a video-call surface, not a form:

- **Both persona tiles are mounted for the whole interview.** The active tile is the round's
  persona (`state = 'hr_round'` → HR, `tech_round` → tech): full opacity, `--live` ring, lit
  name/role label, and the static avatar image for the current `persona.avatarState`. The other
  tile is dimmed with a localized `up next` (before its round) or `done` (after it) label.
  Room-state carries only the active `persona`; the client resolves the second tile from the
  round list it already has, and never invents a second live speaker — the state machine has
  exactly one (K2).
- **`● LIVE` badge** in `--live` while the interview is in `hr_round` or `tech_round`. **There is
  no `REC` indicator** — nothing is recorded (§3.2), and a recording badge on a product that
  records nothing is a lie the user would act on.
- **The current question is a persistent banner**, not a transcript line that scrolls away.
- A `Question k / N` progress indicator driven by `currentIndex` (global 1..N — K2, never
  `order_index`).
- A **collapsible** conversation/transcript panel fed the same `chat_messages`; collapsed state is
  local UI state and survives a refetch (it is not room truth).
- A single answer textbox with a **Submit answer** action (text mode), or the voice controls
  (`voice`). No form feel — the room animates.
- **Round handover** (`hr_round → tech_round`) shows the explicit interstitial ("connecting you to
  the technical interviewer", §15.2 story 6), moves the `--live` ring to the other tile, and
  announces the change through the `aria-live` region (§4.4). The handover is detected from the
  refetched `state`, never predicted client-side.
- **No mascot on this route** (§4.2.1) — a hard exclusion, not a styling preference.

**States for this screen** (§4.3): **loading** — first mount before `['interview', id, 'state']`
resolves renders the room chrome with skeleton tiles, never a blank page; **empty** — a state
with no live `currentQuestion` (e.g. `evaluating`) shows the report-wait view rather than an empty
banner; **error** — a failed state fetch keeps the last known room visible with a non-blocking
retry, because dumping a candidate out of a live interview on one failed request is the worst
possible failure mode here.

**Client-driven avatar state machine (text mode, §3.8).** In text mode the avatar state is
derived from the room lifecycle, with `persona.avatarState` from room-state as the
authoritative sync value on every refetch:

| Lifecycle phase | Avatar state |
|---|---|
| Awaiting the next question from the server (post-submit, generation/advance in flight) | `thinking` |
| The question text is mid-animation (typing itself in) | `speaking` |
| Question fully shown, awaiting the user's input | `listening` |
| Immediately after a successful submit, before `thinking` | `acknowledging` |
| Room mounted, nothing in flight | `idle` |

The five state keys and their images are `ui`/`db` (§3.6); this table is only the text-mode
*trigger* mapping (§3.8). Driven by the `EventAvatarDriver` seam (§3.6, cited); the
`AmplitudeAvatarDriver` is voice-only and gated on §15.1 item 3 — it does not exist in the
MVP.

**Typed-question delivery (§3.8).** A newly delivered question is character-animated into
the panel at **40 characters/second** (a readable pace, not an instant paste), during which
the avatar is `speaking`. Under `prefers-reduced-motion` the animation resolves **instantly**
(§4.4, honoured) and the avatar goes straight to `listening`.
<!-- ponytail: 40 cps is a pinned default, not an IDEA number; §3.8 says only "a readable
     pace". Tunable in one place; raising it never changes behaviour, only feel. -->

**Answer submission.** Submitting posts `{ questionId, transcript, inputMode: 'text' }` (or
`'widget'`, §3.9) for the question at `currentIndex`. The client does **not** advance
optimistically: it awaits the response, then the SSE nudge / mutation success invalidates
`['interview', id, 'state']` and the room re-renders from the refetched truth (K11). An
out-of-turn submit answered with `QUESTION_NOT_CURRENT` triggers a silent refetch, never an
error toast (the user simply sees the current question).

**Progress and end.** When the refetched `state` is `evaluating`, the room transitions to
the report-wait view (§4.3, US-21) showing "preparing your evaluation"; on the completion
nudge the report at `GET /interviews/:id` is fetched. `endedReason` (`cut_short`,
`budget_exhausted`, `time_exhausted`, `completed`) is surfaced as a localized note, not a
raw enum.

**No back / no skip is a server fact, not a hidden button** (US-17, K2): the room offers no
navigation to a past or future question; the server rejection is the real guard.

### 4. Question widgets (§3.9)

When `currentQuestion.kind = 'widget'`, the conversation panel renders the widget instead of
(voice mode) muting the mic; in text mode the textbox is replaced by the widget. On submit
the selection is serialized into `transcript` with `inputMode = 'widget'` (§3.9) — stored
exactly like a spoken/typed answer. The widget *sub-type* is `currentQuestion.widget.kind ∈
{ mcq, ordering, code }`; the client renders the matching control and serializes the selection
to a deterministic readable line (chosen option text / ordered list / code verbatim) in
`transcript`. The render slot and the submit shape are fixed here regardless.

### 5. Report screen (§4.3, US-21)

Reads `GET /interviews/:id` → `{ interview, transcript, report? }`. While `report` is absent
and `state = 'evaluating'`, the report-wait view is shown and the SSE nudge (or a bounded
poll of the same query) resolves it — target **< 60 s** (§8.1). When present, `report.payload`
(the K15 `ReportPayload`, `ai`/`db`-owned) is rendered read-only:

- Single column, expandable per-question cards; every score always carries its `reason`
  (§4.3 — readability first; measure is `ui`, §4.2).
- Renders `overall_impression`, `overall_score`, `strengths[]`, `improvements[]`,
  `rounds[]` (with the optional `note`, e.g. a weak HR round — no elimination, K5), and
  `questions[]` (score, reason, `star_adherence`). Answer duration comes from the
  interview/transcript data (server-derived, K15), not recomputed here.
- **Download PDF** (US-24) is a last-bonus-bucket action (§12): a button that requests the
  worker-rendered PDF via its signed URL when the feature ships; absent, the button is not
  shown. This spec reserves the slot and asserts nothing about the PDF itself (`worker`/K12).

### 6. History / dashboard (US-22, US-23)

`GET /me/interviews` (the `userInterviews` helper → deleted rows never appear, K13) lists
occupation, date, duration, state and score, cursor-paginated. Each row opens
`/interviews/:id`. An in-progress interview offers **Continue** → `/interviews/:id/room`
(US-19). **Delete** calls `DELETE /interviews/:id` and optimistically removes the row, then
invalidates `['me','interviews']`; the row stays visible to admins (soft delete, K13) — the
client asserts nothing about the admin side.

### 7. Admin (§4.3, US-26/27/28/29)

Jotform-density register (`ui`, §4.1/§4.2). Tables and filters over `GET /admin/interviews`
(occupation cluster / state / user; deleted rows shown with a `deleted` badge and cost
intact), a per-interview drill-down over `GET /admin/interviews/:id` (per-call `llm_calls`
rows: provider, model, `prompt_uuid`+version, units, unit_kind, cost, latency; plus security
/ budget / time events for US-29), and a Recharts dashboard over `GET /admin/stats` rendering
K11's five metrics **as returned**. The "which questions are answered weakest" view reads
`weakestQuestions[]` directly (K11/K15).

### 8. Locale switching (§4.5)

The locale toggle (English/Turkish) writes the cookie and re-renders; it changes UI copy and
`errors.*` messages only. It does **not** touch `interviews.language` (the interview language
is a separate axis, §3.4) — a user runs the app in English and interviews in Turkish.

## Failure modes

Frontend is a client app, so most "failures" are transport conditions and API codes it must
handle without ever rendering a raw code (§4.5). Every code below is owned by `backend`/`ai`
(marked †); frontend adds none. Each row is a Stage-2 scenario candidate at the ring noted
in [Acceptance criteria](#acceptance-criteria).

| Condition | Code / signal | UI behaviour |
|---|---|---|
| Any API error envelope | `{ error: { code } }` † | Render `errors.<CODE>` in the active locale; unknown → `errors.UNKNOWN`, never raw |
| Session missing/expired on any authed route | `UNAUTHENTICATED` † | Redirect to `/sign-in`, preserve return path |
| Non-admin reaches an admin route/API | `FORBIDDEN` † | Redirect to `/dashboard`; not-authorized state |
| Out-of-turn / stale answer submit | `QUESTION_NOT_CURRENT` † | Silent state refetch; show the current question, no toast |
| Illegal transition attempted | `INVALID_STATE_TRANSITION` † | Silent state refetch |
| Budget tripped mid-interview | `BUDGET_EXCEEDED` † | Refetch → `evaluating` → report-wait view |
| SSE stream drops | `EventSource` `error` | Native reconnect; on `open`, one state invalidation; UI keeps last-known state meanwhile |
| Report not ready yet | `state = 'evaluating'`, `report` absent | Report-wait view until the completion nudge (bounded fallback poll of the same query) |
| Report generation failed | `state = 'failed'` | Localized "we couldn't finish your report" with a *try again* affordance (K10) |
| Unverified user starts an interview (flag on) | `EMAIL_NOT_VERIFIED` † | Route to `/verify-email`, preserving the typed listing so nothing is retyped |
| Verify/reset link already used or expired | `EMAIL_TOKEN_INVALID`, `EMAIL_TOKEN_EXPIRED` † | Inline on the screen with a *request a new link* action; never a dead end |
| Resend pressed inside the cooldown | `EMAIL_RESEND_COOLDOWN` † | Button stays disabled, remaining seconds shown from the response |
| Onboarding card saved while signed out | `UNAUTHENTICATED` † | Redirect to `/sign-in`; on return the resumed step is whatever the **server** profile says, so nothing typed-and-saved is lost |
| CV PDF unreadable | `PDF_TEXT_TOO_SHORT` † | Non-blocking notice; the CV is optional and onboarding continues |
| Camera/mic permission denied on pre-join | `getUserMedia` rejection | Offer **continue in text** (the §3.8 downgrade path); never a blocked screen |
| Network/5xx with no envelope | HTTP status | Generic `errors.UNKNOWN`; React Query retry/backoff on idempotent GETs only, never on submit |

## Observability

The SPA emits **no** K6 structured server logs — K6 is a server contract (K6). Every
debuggable user action is already an API call logged server-side under its `traceId` and
`interviewId`; the client adds nothing an admin searches by. The client therefore keeps no
log pipeline of its own. Where a request fails, the surfaced message is a localized
`errors.*` string (never a code or a stack), and correlation to server logs is via the
interview the user is in (`interviewId`), which the admin already has (US-28). No transcript,
PII, token or listing content is ever placed in a client console line or a URL query string.

## Security

Frontend sits on the browser trust boundary; what crosses it and the rules that hold:

- **The session cookie is `httpOnly`** (K8, §7.2) — JavaScript cannot read it, so no token
  ever lives in client memory, `localStorage`, or a URL. All authenticated calls rely on the
  cookie being sent same-origin through the edge (K14); the client stores no credential.
- **All server- and LLM-originated content is rendered as text, never HTML.** Questions,
  report prose, transcript and persona copy are attacker-influenceable (the job listing
  reaches the model, §7.1) and are never passed to `dangerouslySetInnerHTML` or an
  equivalent — the client is not a second injection surface. `next-intl` interpolation is the
  only templating, over developer-authored keys.
- **CSRF** is `SameSite=Lax` + a server-side `Origin`/`Referer` check (`backend`, §7.2); the
  client's obligation is to issue state-changing requests same-origin only, which the route
  map guarantees (no cross-origin API base — §11.3).
- **CSP** (`default-src 'self'`, self-hosted `next/font`, no external script/font origin) is
  set at the edge (§7.4, `infra`); the client must not introduce an inline-script or external
  asset dependency that would need the policy widened.
- **No environment-conditional behaviour** (§11.3): the app reads origins and the default
  locale from env/config (`PUBLIC_ORIGIN`, `INTERNAL_API_URL`, `NEXT_PUBLIC_DEFAULT_LOCALE`)
  but branches no business logic on the environment.
- Camera/recording concerns (§3.2 — off by default, never uploaded) belong to the voice room
  (`voice`); text mode captures no device media at all. The pre-join preview stream is bound to a
  local `<video>` only — no peer connection, no upload, no recording.
- **Verification and reset tokens live in the URL path, never in client storage or a log.** The
  confirm screens post the token once and drop it; the client keeps no copy, appends it to no
  analytics call, and puts it in no console line.
- **The reset screen never reveals whether an account exists** — the success copy is identical in
  both cases (K8.6), so the client must not branch on the response shape.
- **CV and profile data is displayed, never re-broadcast.** The CV PDF is reached only through a
  server-issued signed URL (K12); the client stores no copy and puts no filename or profile field
  in a URL query string. `date_of_birth` is rendered only in the onboarding form that collects it.

## Open questions

Empty. Both forks this spec raised were resolved during authoring and are recorded below;
neither is a new requirement.

1. **Widget descriptor + answer serialization (§3.9).** `currentQuestion.widget` is a
   discriminated object `{ kind: 'mcq' | 'ordering' | 'code', options?: string[], language?:
   string }` (`null` for non-widget questions); the answer serializes to a deterministic
   readable line — the chosen option text (`mcq`), the ordered option list (`ordering`), or the
   code verbatim (`code`). `widget.kind` is a room-state sub-type, **not** a `QuestionKind` enum
   change. Pinned jointly with the `backend` room-state contract.
2. **Report-wait fallback when no SSE nudge arrives (K10, §8.1).** On the `evaluating` view the
   client polls `GET /interviews/:id` at a fixed interval with backoff, capped at the §8.1 60 s
   budget, cancelled the instant an SSE nudge arrives. The SSE path stays primary; this is the
   degraded-transport tail only.

## Acceptance criteria

Each is observable from outside the code. **Verification surface note (§5.3):** Cucumber
drives the HTTP API, not a browser, so the criteria below are verified at the **component /
integration** ring (React Testing Library over a mocked API + `EventSource`) or as a handful
of **Playwright smokes**, not as acceptance-ring Gherkin. They are still phrased as observable
outcomes; the ones that reduce to an API assertion (server behaviour) already live in the
`backend`/`ai` specs and are not duplicated here.

1. Given the API returns `{ error: { code: 'EMAIL_TAKEN' } }`, the UI renders the
   `errors.EMAIL_TAKEN` message in the active locale; switching the locale to `tr` renders the
   Turkish message for the same code; an **unrecognized** code renders `errors.UNKNOWN` and
   the raw code string never appears in the DOM.
2. A `401 UNAUTHENTICATED` on any authenticated route redirects to `/sign-in` and preserves
   the intended return path; a `403 FORBIDDEN` on an admin route lands on `/dashboard`/not-
   authorized without exposing admin data.
3. On any SSE `{ type }` event, the room refetches `['interview', id, 'state']` and renders
   from the response; the same render results regardless of the event's payload contents
   (payload is ignored). On `EventSource` disconnect then reconnect, exactly one additional
   state refetch occurs on `open`.
4. Mounting `/interviews/:id/room` with no prior client state renders the correct current
   question, progress `currentIndex / targetQuestionCount`, persona and conversation history
   purely from `GET /interviews/:id/state` (resume-after-refresh, US-19).
5. The progress indicator shows `currentIndex` (global 1..N), not a per-round `order_index`:
   the first technical question in an 8-question interview with 3 HR questions displays `4 / 8`.
6. Submitting an answer posts `{ questionId, transcript, inputMode: 'text' }` for the question
   at `currentIndex` and does **not** advance the UI until the refetched state confirms it; a
   `409 QUESTION_NOT_CURRENT` response produces a silent state refetch and no error toast.
7. A newly delivered question animates in at the pinned character pace with the avatar in
   `speaking`; under `prefers-reduced-motion` it appears instantly and the avatar goes to
   `listening`.
8. In text mode the avatar state follows the §3.8 lifecycle table (`thinking` while awaiting
   the next question, `speaking` while typing, `listening` while awaiting input,
   `acknowledging` immediately after submit), and re-syncs to `persona.avatarState` on every
   refetch.
9. When room-state reports `kind = 'widget'`, the widget slot replaces the textbox and a
   submit posts `inputMode = 'widget'` with the selection encoded in `transcript` as the
   deterministic readable line for `widget.kind` (option text / ordered list / code verbatim);
   a non-widget question renders the textbox.
10. When the refetched state is `evaluating`, the room shows the report-wait view; when
    `GET /interviews/:id` returns a `report`, the report screen renders `overall_impression`,
    `overall_score`, `strengths`, `improvements`, `rounds[]` (including an optional `note`) and
    per-question `score`/`reason`/`star_adherence` read-only, with each score carrying its
    reason.
11. The dashboard lists only non-deleted interviews (deleted rows absent), paginates by
    `nextCursor`, offers **Continue** for an in-progress interview, and **Delete** removes the
    row optimistically then reconciles via `['me','interviews']` invalidation.
12. The admin dashboard renders K11's metrics exactly as `GET /admin/stats` returns them
    (`averageDurationMs`, `completed`/`unfinished`, `totalTokens`, `perOccupation[]`,
    `weakestQuestions[]`) with no client-side recomputation; the admin interview list shows
    deleted rows with a badge and their cost intact.
13. The locale toggle changes UI copy and `errors.*` messages only and leaves
    `interviews.language` untouched; LLM content (questions, report, transcript) always renders
    in the interview language, never through `next-intl`, and never as HTML.
14. No server- or LLM-originated string is rendered via `dangerouslySetInnerHTML`; the session
    cookie is never readable from client JavaScript (no token in `localStorage`, memory, or a
    URL).
15. **First-run routing (K8.7).** A user with `onboardingCompletedAt = null` lands on
    `/onboarding/[first unfilled step]` after sign-in; one with onboarding done and
    `interviewCount = 0` lands on `/interviews/new`; anyone else lands on `/dashboard`. Deep-linking
    to `/onboarding/3` with an empty profile redirects to step 1.
16. **Per-card persistence.** Completing card 1 and then unmounting the app (no `complete` call)
    leaves the card-1 fields readable from `GET /me/profile`, and re-entering onboarding resumes at
    card 2 — with no reliance on `localStorage`.
17. **Skip.** *Skip for now* on any card calls `POST /me/profile/complete`, leaves the remaining
    profile fields unset, and routes onward; no error state is rendered for a partial profile.
18. Education rows cap at **5**: the *+ Add another* control is unavailable at 5 rows, and a
    `PATCH /me/profile` carrying more is rejected by the server (`VALIDATION_ERROR`) and surfaced
    inline.
19. **Verification screens.** `/verify-email` renders the pending state with a resend countdown;
    pressing resend inside the cooldown keeps the button disabled and shows the remaining seconds
    from `EMAIL_RESEND_COOLDOWN`; `/verify-email/[token]` with a used or expired token renders the
    failure **with a request-a-new-link action** and the token appears in no console line, no
    storage and no subsequent request.
20. **Reset screens.** `/forgot-password` renders the same success copy for a known and an unknown
    email; completing `/reset-password/[token]` routes to `/sign-in` with the "signed out
    everywhere" note (K8.6).
21. `EMAIL_NOT_VERIFIED` on `POST /interviews` routes to `/verify-email` **and the typed listing
    text is still present** when the user returns to setup.
22. **Setup screen.** The suggestion chips prefill the textarea with **no** network request; the
    three option cards perform their local action (clear / prefill from profile / load the sample);
    no control for practice mode, a template library or URL import exists in the DOM (§4.3.1); and
    every error on this screen preserves the typed listing text.
23. **Room panel.** Both persona tiles are present throughout; the tile matching the round from
    room-state carries the `--live` ring and lit label while the other is dimmed and labelled
    `up next` or `done`; a `hr_round → tech_round` refetch moves the ring, shows the handover
    interstitial and fires one `aria-live` announcement; the `LIVE` badge is present during an
    active round and **no `REC` indicator exists anywhere in the DOM**; the current question is
    rendered in the persistent banner; collapsing the transcript survives a state refetch.
24. **Pre-join.** A voice-mode interview routes through `/interviews/:id/pre-join`, where the
    camera is **off** by default and the preview stream is attached to a local `<video>` with no
    peer connection or upload; a permission denial offers *continue in text*; a text-mode
    interview visiting the route redirects to the room.
25. **Mobile at 390 px.** Setup stacks its option cards below a sticky primary action with
    horizontally scrolling chips; the room shows one full-size active tile with the other persona
    and self-camera in a strip, the transcript as a collapsed bottom sheet, and a control bar
    fixed to the bottom edge that does not auto-fade. Neither screen scrolls horizontally.
26. **Mascot placement.** Each of landing, register, sign-in, verify, reset and the three
    onboarding cards renders exactly its assigned pose (§4.2.1) with a localized `alt`, and
    preloads only that pose; no mascot image appears on the room, report or admin routes.
