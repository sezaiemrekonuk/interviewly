## Scope

This spec pins the persistent data layer: the complete `schema.prisma` (K13), its enums,
the §8.1 indexes, the soft-delete repository-helper contract, the `spent_usd`/`llm_calls`
single-transaction rule, and the Prisma Migrate conventions that stop week-one collisions
(§5.2). It is the section every other area reads instead of asking what a column means. The
entire schema — including tables no feature ledger has reached — lands in foundations task
F02 (`F-b`); this spec is that task's contract.

**Not in this spec** (named owner):

- Endpoint request/response shapes, session issuance, HTTP status mapping — `backend`.
- Who writes an `llm_calls` row, prompt compilation, budget/selection logic beyond the
  transaction rule — `ai`.
- Object storage, buckets, signed URLs, MinIO/S3 — `infra` (K12); only the *key* columns
  (`storage_key`, `pdf_key`, `avatar_set`) live here.
- Migrations that add indexes or nullable columns for a feature — the feature's ledger,
  each in its own migration (§5.2).
- Component props, charts, locale strings — `frontend`, `ui`.

## Contracts

### Session-resolved forks (decided beyond IDEA.md, this session)

IDEA.md did not settle these four; they were decided during authoring and are recorded here
so every downstream claim is traceable. They are not new requirements — they make K13
implementable.

1. **`occupation_clusters` is a seeded reference table.** `interviews.occupation_cluster_id`
   is an FK to it, giving K11's admin grouping a stable key and §8.1 a clean index. K13's
   prose `occupation_cluster` becomes this relation.
2. **Enums are Prisma native enums** (Postgres enum types), matching K13's `[a|b]` bracket
   notation and enforcing membership in the database. Consequence: adding an enum value is a
   structural change, so only F02 may do it (§5.2).
3. **Money is `Decimal(12,6)`; `llm_calls.units` is `Decimal(12,3)`.** Sub-cent token costs
   accumulate without rounding drift; units carry fractional seconds.
4. **Primary keys are `cuid`** (Prisma default) on every table. Satisfies K15's string
   `question_id`. The voice `nonce` is a separate opaque secret, not a PK.

### JSONB payload shapes (owned elsewhere, cited so consumers agree)

- `users.profile` — the account onboarding payload (§3.3 layer 1):
  `{ fullName?, jobTitle?, dateOfBirth?, education?: [{ school, degree, field, graduationYear }],
  hobbies?: string[], interestsText?, cvText? }`. Partial is normal (each card saves on its own);
  `null` means every card was skipped. **`dateOfBirth` never leaves the database toward `ai` and
  never enters a log line** (§3.3, §7.2) — `backend` strips it when building `candidate_profile`.
- `interviews.candidate_profile` — the **merged snapshot** taken at
  `POST /interviews/:id/profile`: `{ account: <users.profile minus dateOfBirth>, cvText?,
  perInterview: { yearsExperience?, interests?, targetSeniority? } }`; `null` when both layers were
  skipped, never `{}`. A snapshot rather than a join, so a later profile edit cannot change what an
  older report was reasoned from (§3.3).
- `answers.scores` — K4 shape: `{overall, relevance, depth, structure, star_adherence, reasons[]}`.
- `reports.payload` — K15 Zod schema.
- `personas.avatar_set` — `{ [AvatarState]: storageKey }` (§3.6), keys under `personas/{id}/`.
- `questions.candidates` — K4's two unselected candidates, retained for admin analysis.

These are validated by the owning module (backend/ai), not the database. The db layer stores
them as opaque `jsonb`.

### Indexes (§8.1)

```
interviews(user_id, created_at)
interviews(occupation_cluster_id)      // FK-backed; the K11 admin grouping key
interviews(state)
llm_calls(interview_id)
questions(round_id, order_index)       // UNIQUE — order_index is unique within a round
email_tokens(user_id, kind)            // K8.6 — cooldown/latest-token lookups
uploads(user_id, kind)                 // §3.3 — "this user's CV" without a table scan
```

`sessions` is looked up by opaque cookie → the token PK is the lookup; no extra index.
`uploads.sha256` and `users.email_lower` carry UNIQUE indexes by their constraint.

### Repository-helper contract (K13 soft-delete rule)

F02 ships, and user-facing modules must use, helpers that bake in `deleted_at IS NULL`:

- `userInterviews(userId)` → non-deleted interviews for a user, paginated.
- `activeInterview(id)` → single non-deleted interview or `null`.

Admin/analytics reads that must count deleted interviews (K11: "Total tokens … deleted
interviews included") bypass the helper deliberately and say so at the call site.
`prisma.interview.findMany` is never called directly from a user-facing module (K13);
convention, caught in review.

## Behaviour

Numbers and rules, stated so two implementers produce the same schema.

1. **Soft delete.** Only `interviews` has `deleted_at`. Deletion is `UPDATE … SET deleted_at
   = now()`, never `DELETE`. No other table is soft-deletable; there is no hard user
   deletion in scope, so no cascade is needed.
2. **Foreign keys are `ON DELETE RESTRICT`, no cascades.** Because deletion is soft and rows
   are never hard-deleted, RESTRICT can never fire in normal operation; it exists as a
   guard, not a workflow.
3. **`spent_usd` is incremented in the same transaction that inserts the `llm_calls` row**
   (K13, §7.3). The pre-call budget check re-reads `spent_usd` inside that transaction. A
   read-outside / write-inside split is a defect: two concurrent calls both pass a stale
   check. This is a db-level contract (the transaction boundary), enforced by `ai`.
4. **`current_index` advancement is an optimistic guarded update** (K2):
   `UPDATE interviews SET current_index = $next WHERE id = $id AND current_index = $expected`
   via Prisma `updateMany`; `count === 0` → `QUESTION_NOT_CURRENT`. No row lock, no
   `FOR UPDATE`. `current_index` is global `1..N`; `questions.order_index` is per-round
   `1..n`; `current_index = (round is tech ? hr_question_count : 0) + order_index`.
5. **State transitions** are validated by `backend`, but the db stores only the current
   `state` + `ended_reason`; any transition not in K2's table is rejected upstream with
   `INVALID_STATE_TRANSITION`. `ended_reason` is set exactly when entering `evaluating` or
   `abandoned`.
6. **`email_lower` is the lowercased email**, UNIQUE. The application lowercases before
   write; a duplicate insert surfaces the unique-constraint violation as `EMAIL_TAKEN`
   (K8.5).
7. **`sha256` deduplicates uploads** (K12): UNIQUE; the same file twice reuses the row. The
   dedup key is the bytes, not the `kind` — the same PDF submitted once as a listing and once as a
   CV is one row, and the referencing side (`interviews.upload_id` / `users.cv_upload_id`) is what
   records the role it played.
7a. **`email_tokens` stores hashes, never tokens** (K8.6). `token_hash` is `sha256(token)` and is
   UNIQUE, so a lookup is one indexed comparison. Consumption is a **guarded update**
   (`… SET consumed_at = now() WHERE id = $id AND consumed_at IS NULL`) — `count === 0` means a
   concurrent request already consumed it, which is how a double-clicked verification link resolves
   to exactly one success. Expiry is `expires_at` and is checked in the same statement's predicate
   or immediately after the read; a consumed or expired row is never deleted, so the audit survives.
7b. **A password reset revokes every session of the user** in the same transaction that rewrites
   `password_hash` (K8.6). A reset that leaves an attacker's session alive is not a reset.
7c. **`users.cv_upload_id` is a pointer, not a history.** Uploading a new CV repoints it; the
   previous object stays in the bucket (content-addressed, K12). There is no per-user CV list,
   because nothing in the product asks for one.
8. **`budget_usd` defaults to `0.50`** (§7.3). `spent_usd` and `current_index` default to
   `0`.
9. **Timestamps are `timestamptz`.** Durations derive from columns, never stored redundantly
   except `answers.duration_ms` (K15: server-set at delivery/submission).
10. **Migration protocol (§5.2).** The whole schema lands in F02. Feature ledgers may add
    **indexes and nullable columns only**, each in its own timestamped Prisma migration,
    rebased before merge. New table, dropped column, changed relation, or new enum value is a
    change to F02's scope — discussed, not merged. This is the rule that keeps
    `docker compose up` working on a fresh clone (§10).
11. **Seed (`prisma/seed.ts`, K13/§3.6).** `docker compose up` + seed yields a working room
    with no manual step: one demo admin (email+password, `role=admin`), the
    `occupation_clusters` reference rows, both `personas` with `avatar_set` keys and uploaded
    avatar objects, **the shared mascot set (all five `MascotPose` keys) uploaded under
    `mascot/`**, **one seeded sample job listing** (the setup screen's *Try a sample listing*
    option, §4.3.1), and one sample interview. The admin account has a non-null `password_hash`
    (K8.5) **and a non-null `email_verified_at`** — a seeded account that cannot start an interview
    when `EMAIL_VERIFICATION_REQUIRED=true` would make the demo depend on reading a mailbox (K8.6).
12. **Shadow database.** Prisma Migrate's shadow database is created by `db/` init SQL (repo
    convention); this spec assumes it exists and does not define it.

## Failure modes

Every row is a Stage-2 scenario candidate. Codes are stable `SCREAMING_SNAKE_CASE` from the
shared registry (§4.5); the db layer's job is to make the *condition* detectable, the owning
module returns the code.

| Condition | Code | HTTP | Recovery |
|---|---|---|---|
| Duplicate `email_lower` on register | `EMAIL_TAKEN` | 409 | Sign in or use another email (K8.5) |
| `email_tokens` guarded consume matched 0 rows (absent or already consumed) | `EMAIL_TOKEN_INVALID` | 400 | Request a new link (K8.6) |
| `email_tokens.expires_at` in the past | `EMAIL_TOKEN_EXPIRED` | 400 | Request a new link (K8.6) |
| `current_index` guarded update matched 0 rows | `QUESTION_NOT_CURRENT` | 409 | Refetch `GET /interviews/:id/state`, retry (K2) |
| Transition absent from K2's table | `INVALID_STATE_TRANSITION` | 409 | No state change; client resyncs (K2) |
| Pre-call budget check (in-tx) shows `spent_usd ≥ budget_usd` | `BUDGET_EXCEEDED` | 402 | No call; interview → `evaluating`, `ended_reason=budget_exhausted` (§7.3) |
| Upload with an already-stored `sha256` | *(not an error)* | — | Existing `uploads` row reused (K12) |

`BUDGET_EXCEEDED` is surfaced by `ai`/`backend`; it is listed here because the detecting
read is a db read inside the recording transaction. No code in this table is a display
string.

## Observability

The db layer emits no log lines of its own; it is a library, not a service. But the columns
below exist **so the events other areas log (K6) are answerable from data**, which §15.2
(story 16) requires to work from `docker compose logs` when Kibana is down:

- `llm_calls.trace_id` and `chat_messages.trace_id` — join a log line's `traceId` to the row
  that produced it.
- `llm_calls(prompt_uuid, prompt_version)` — trace a bad report to a prompt version (K9),
  rollbackable and A/B comparable.
- `interviews.id` (`interviewId`) — the second mandatory key on every K6 log line; every
  interview-scoped table FKs back to it.
- `report_questions` — denormalises K15's `questions[]` so the admin "which questions are
  answered weakest" query needs no jsonb traversal.

An admin debugging a report searches by `interviewId`, then `trace_id`, then
`(prompt_uuid, prompt_version)`.

## Security

The db sits at the persistence trust boundary. What crosses it and the rules that hold there:

- **No secrets, PII, tokens or PDF content beyond what a column is defined to hold.**
  `password_hash` holds an argon2id hash (K8), never plaintext. `email_tokens.token_hash` holds
  `sha256(token)`, never the token (K8.6). `uploads` stores a `storage_key`, never bytes.
  `users.profile` holds `date_of_birth` and `cv_text` — both PII, both barred from log lines, and
  `date_of_birth` additionally barred from every prompt (§3.3). Log lines never echo these columns
  (§7.2, K6).
- **`voice_sessions.nonce` is an unguessable secret**, paired with `interviewId` to
  authorise webhooks (§3.5). It is not a PK and is never returned in a list endpoint.
- **Deleted interviews must not leak** into a user's list — the whole reason the soft-delete
  repository helper exists rather than relying on discipline (K13). This is a visible failure
  of a 5-point criterion if it regresses.
- **Signed-URL vs public-read access** is enforced at the storage layer (K12/`infra`), not
  here; the db only stores keys and never a URL.

Empty. The four forks IDEA.md left open (occupation-cluster modelling, enum representation,
money precision, PK type) were resolved this session and recorded under *Session-resolved

- `QuestionKind` value set — provisionally `{open, behavioral, technical, widget}` from §3.9

Neither blocks F02: both have a defensible default that ships, and a change to either is a
scoped, reviewed enum migration, not a free-for-all.

## Acceptance criteria

Each is observable from outside the code — a migration run, a query, or a constraint
violation.

1. `prisma migrate deploy` on an empty database creates all 15 tables (`users`, `sessions`,
   `email_tokens`, `personas`, `occupation_clusters`, `interviews`, `interview_rounds`,
   `questions`, `answers`, `reports`, `report_questions`, `voice_sessions`, `uploads`,
   `chat_messages`, `llm_calls`) and every enum type, with no error.
2. Every enum column rejects a value outside its declared set at the database level (insert
   with a bad enum literal fails).
3. Inserting a second `users` row with an existing `email_lower` fails the unique
   constraint; a second `uploads` row with an existing `sha256` fails likewise.
4. `interviews.budget_usd` defaults to `0.500000` and `spent_usd` to `0.000000` when
   unspecified; both hold six decimal places without truncation.
5. All five §8.1 indexes exist after migration, and `questions(round_id, order_index)` is
   UNIQUE (a duplicate `order_index` within a round fails).
6. `userInterviews(userId)` never returns a row whose `deleted_at` is non-null;
   soft-deleting an interview removes it from that helper's result while the row remains in
   the table.
7. The guarded `current_index` update returns `count = 0` (→ `QUESTION_NOT_CURRENT`) when
   `current_index` no longer equals the expected value, and `count = 1` otherwise.
8. Incrementing `spent_usd` and inserting the matching `llm_calls` row in one transaction
   are atomic: a rollback leaves neither; the pre-increment `spent_usd` read sees the
   committed value.
9. Every interview-scoped table (`interview_rounds`, `questions` via round, `answers` via
   question, `reports`, `report_questions`, `voice_sessions`, `chat_messages`, `llm_calls`)
   resolves to a single `interviews.id`, and each carries the columns needed to answer a K6
   log line by `traceId` where the K13 schema names one.
10. `prisma/seed.ts` on a fresh database produces: one `role=admin` user with a non-null
    `password_hash`, the `occupation_clusters` reference rows, two `personas` with populated
    `avatar_set`, and one sample interview — with no manual upload step.
11. All foreign keys are `ON DELETE RESTRICT`; no cascade delete exists on any relation.
12. `report_questions` can be queried for lowest-scoring `question_id`s without reading any
    jsonb column (the K11 admin statistic is a plain relational query).
13. `email_tokens.token_hash` is UNIQUE; the guarded consume returns `count = 1` on the first call
    and `count = 0` on every subsequent one for the same row, and the consumed row is retained
    (never deleted) with its `consumed_at` set (K8.6).
14. A password-reset transaction that rewrites `password_hash` and sets `revoked_at` on all of that
    user's `sessions` is atomic — a rollback leaves both unchanged, and after commit no pre-reset
    session row is un-revoked.
15. `users.profile` accepts a partial object (one card's keys only) and merging a second card
    preserves the first card's keys; `users.cv_upload_id` resolves to an `uploads` row whose
    `kind = 'cv'`.
16. Both `email_tokens(user_id, kind)` and `uploads(user_id, kind)` indexes exist after migration,
    and `MascotPose` and `UploadKind` reject values outside their declared sets.
17. `prisma/seed.ts` additionally produces the five-pose mascot set under `mascot/`, the sample job
    listing, and a demo admin whose `email_verified_at` is non-null.
