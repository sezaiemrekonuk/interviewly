## Scope

This spec pins the `api` HTTP surface Interviewly exposes to the browser and to
neighbouring areas: the auth/session endpoints (K8, K8.5), the interview lifecycle
endpoints driven by the K2 server-side state machine, the admin read endpoints, the SSE
nudge stream (K11), upload validation and text extraction (K12/§7.2), and the cross-cutting
controls — rate limiting, CSRF/origin, ownership authorisation, Zod validation, cost/budget
enforcement (§7.3), reliability probes and timeouts (§8.3). It is the section a neighbouring
area reads instead of asking what an endpoint returns or when a state transition fires. The
module boundaries `auth` / `interview` / `admin` / `ai` are folders inside `api` (K1);
reaching into another module's repository or tables is forbidden.

**Not in this spec** (named owner):

- `schema.prisma`, enums, indexes, soft-delete repository helpers, the
  `spent_usd`/`llm_calls` single-transaction rule as a *db contract* — `db` (K13). This spec
  consumes those helpers and honours that transaction boundary; it does not define them.
- Prompt compilation, the LLM call itself, provider fallback, the report/question/scoring
  content, K4 candidate selection — `ai` (K9, K15, §3.7, §7.1). Backend orchestrates *when*
  generation happens and enforces the *pre-call budget check*; `ai` owns *how* the call is
  made and what it returns.
- Object storage, buckets, signed URLs, MinIO/S3, the Caddyfile, `compose.yaml`, the
  `tunnel` service, CSP headers — `infra` (K12, K14, §7.4). Backend receives an upload,
  validates it, extracts its text and hands bytes to the storage layer; the bucket and the
  5-minute signed URL are `infra`.
- Voice session token minting and the `/webhooks/elevenlabs/*` payload/HMAC contract —
  `voice` (K3, §3.5), authored last (§12). Backend **routes** `/webhooks/*` to the voice
  module and owns nothing inside those handlers here; the row-level auth data
  (`voice_sessions`) is `db`.
- Report *generation*, PDF *rendering*, the 24 h `abandoned` sweeper, voice-usage
  reconciliation, **and mail rendering/delivery** — `worker` (K10, K15, K8.6). Backend **enqueues**
  the report and `email.send` jobs and **serves** the finished report; it runs neither job and
  never opens an SMTP connection.
- Components, charts, locale strings, the Recharts metric *rendering* — `frontend`, `ui`
  (K11, §4). Backend returns the numbers; K11's metric *definitions* are owned by
  `frontend` and cited, not re-decided, here.

**Traceability note.** §2 and `USER_STORIES.md` US-25 cite "K8.4" for the admin
password-only rule; **no K8.4 section exists in IDEA.md**. The rule lives in the *Admin
restriction* bullet of **K8**, and this spec cites K8. Flagged so F01 does not chase a
missing section.

## Contracts

Every endpoint validates its body with Zod at entry (§7.2). Every failure returns a stable
code from the shared registry (§4.5) in a JSON envelope `{ "error": { "code": "…" } }` —
**never a display string**. Codes new to the registry are defined in [Failure modes](#failure-modes);
F01 owns the registry file and collects them. All non-`GET` requests require the session
cookie (except `/auth/register`, `/auth/login`, `/auth/google*`) and an `Origin`/`Referer`
matching `PUBLIC_ORIGIN` (§7.2 CSRF).

### Session cookie (K8, §7.2)

An opaque token in a `httpOnly`, `Secure`, `SameSite=Lax` cookie, backed by a `sessions`
row. 7-day expiry, **sliding renewal** on each authenticated request. Server-side revocation
is a `revoked_at` write. No JWT, no refresh-token family (K8, rejected).

`users.cv_upload_id` and `users.profile.cv_text`; the object itself is **retained** in the private
bucket (K12) so a re-parse never asks the user to upload again.

#### Room-state shape

`GET /interviews/:id/state` returns the complete room state so the client can refetch on
every SSE event and on reconnect (K11 — SSE carries a nudge, not state). Resume-after-refresh
falls out of this same shape (US-19).

```jsonc
{
  "interviewId": "…",
  "state": "hr_round",                 // K2 InterviewState
  "mode": "text",                      // voice|text; downgrade-only (§3.8)
  "currentIndex": 3,                   // global 1..N (K2)
  "targetQuestionCount": 8,
  "endedReason": null,                 // set on evaluating|abandoned (K2)
  "language": "tr",                    // §3.4
  "persona": { "role": "hr", "name": "…", "avatarState": "listening" },  // §3.6
  "currentQuestion": {                 // null when state has no live question
    "id": "…", "text": "…", "kind": "open", "widget": null,             // §3.9
    "deliveredAt": "…"                 // duration clock start (K15)
  },
  "transcriptCursor": 6                // client fetches chat_messages up to here (K11)
}
```

`currentQuestion.widget` is `null` unless `currentQuestion.kind = 'widget'`, in which case it
is a discriminated descriptor `{ kind: 'mcq' | 'ordering' | 'code', options?: string[],
language?: string }` (§3.9). The client renders the matching control and, on submit, serializes
the choice into `answers.transcript` as a deterministic readable line — the chosen option text
(`mcq`), the ordered option list (`ordering`), or the code verbatim (`code`) — posted as
`{ questionId, transcript, inputMode: 'widget' }`. `widget.kind` is a room-state sub-type, not
a `QuestionKind` enum value, so it is **not** an F02 schema change.

#### Admin stats

Numbers computed to K11's fixed definitions — cited, not re-decided:

- `averageDurationMs` = `ended_at − started_at`, `completed` only.
- `completed` = `state = 'completed'` (`cut_short` counts as completed and is broken out
  separately); `unfinished` = `abandoned` + `failed`.
- `totalTokens` = `input_tokens + output_tokens` from `llm_calls`, **deleted interviews
  included**.
- `perOccupation[]` = grouped by `occupation_cluster`, labelled with the most frequent
  `occupation` in that cluster.
- `weakestQuestions[]` = lowest-scoring `question_id`s from `report_questions` (plain
  relational query, no jsonb traversal — K15).

## Behaviour

Numbers, not adjectives. Two implementers reading this produce the same server.

### 1. State machine (K2)

The transition table is authoritative. Any `(from → to)` not listed is rejected with
`INVALID_STATE_TRANSITION` (`409`); no state change occurs.

| From | To | Trigger (endpoint / event) |
|---|---|---|
| `created` | `profiling` | `POST /interviews` accepted |
| `profiling` | `hr_round` | `POST /interviews/:id/profile` (submit or skip) |
| `hr_round` | `tech_round` | HR questions exhausted (last HR answer) |
| `hr_round` \| `tech_round` | `paused` | provider unavailable during a generation/scoring call (§8.3) |
| `paused` | `hr_round` \| `tech_round` | `POST /interviews/:id/resume`, dependency recovered |
| `hr_round` \| `tech_round` | `evaluating` | last question answered, **or** `cut_short` (K5), **or** budget/time exhausted |
| `evaluating` | `completed` | report job reports ready (worker → SSE) |
| `evaluating` | `failed` | report retries exhausted (K10) |
| any non-terminal | `abandoned` | 24 h inactivity — set by the worker sweeper, not by an endpoint |

`ended_reason ∈ {completed, cut_short, budget_exhausted, time_exhausted, abandoned, error}`
is set exactly when entering `evaluating` or `abandoned`.

### 2. `current_index` and the guarded advance (K2)

- `current_index` is **global, 1..N** across both rounds; `questions.order_index` is
  per-round. `current_index = (round is tech ? hr_question_count : 0) + order_index`.
- Advancement is an optimistic guarded update via the db helper:
  `UPDATE interviews SET current_index = $next WHERE id = $id AND current_index = $expected`
  (`updateMany`). `count === 0` → the answer targeted a non-current question →
  `QUESTION_NOT_CURRENT` (`409`), no state change. No row lock (K2). The `questionId` in the
  answer body must resolve to the row at `current_index`; a mismatch is the same rejection.

### 3. Question generation orchestration (§3.7)

- Backend decides the split at setup: `hr = max(2, round(N * 0.4))`, `tech = N − hr`,
  returned in the `POST /interviews` response and shown in the lobby before commit.
- **HR batch** is generated on `profiling → hr_round`, one `ai` call, inserted as
  `questions` rows `order_index` 1..hr. Target < 8 s (§8.1), covered by the lobby wait.
- **Tech batch** is generated **during** the HR round (triggered after HR generation
  succeeds), so the round handover is never a loading screen.
- Backend calls the `ai` module for the batch; `ai` owns prompt compilation, the schema and
  the provider. Backend owns row insertion and the state walk. K4 (bonus) later rewrites the
  *next unasked* row's content in place — backend never inserts or deletes rows mid-round,
  which is why MVP and K4 share a schema.

### 4. Answer submission flow (`POST /interviews/:id/answers`)

In order, within the request:

1. Validate body (Zod). Resolve the interview (ownership) and its current question.
2. Guarded advance check (§2). Mismatch → `QUESTION_NOT_CURRENT`.
3. Record the `answers` row: `transcript`, `input_mode`, `started_at` = the current
   question's `deliveredAt`, `answered_at` = now, `duration_ms` = the difference (K15 —
   server-set, no audio needed).
4. Append a `chat_messages` row for the answer.
5. **Language detection** (§3.4): run the cheap heuristic on this transcript; on **two
   consecutive** answers in a language ≠ `interviews.language`, update `interviews.language`,
   instruct the persona to continue in it, and discard/regenerate any pre-generated K4
   candidates (they are in the wrong language). *(Thresholds: non-Latin script ratio > 0.6, else
   stop-word hit ratio ≥ 0.15; below both is ambiguous and keeps `interviews.language`.)*
6. Advance `current_index`. If the round's questions are exhausted, transition
   (`hr_round → tech_round`, or `→ evaluating` if tech was last).
7. On entering `evaluating`, set `ended_reason`, enqueue the report job (K10), and emit the
   SSE nudge.

### 5. Cost and budget enforcement (§7.3)

- **Pre-call ceiling (text path).** Before **any** `ai` call the interview would incur,
  backend requires the check to read `spent_usd` **inside** the transaction that would record
  the `llm_calls` row (the db contract, K13). If `spent_usd ≥ budget_usd` (default $0.50): no
  call, transition to `evaluating`, `ended_reason = 'budget_exhausted'`, generate the report
  from what exists. The submitted answer is **not** lost. The API returns `BUDGET_EXCEEDED`
  (`402`) on the triggering request and the client refetches state.
- **Daily cap.** A user may start **5** interviews per rolling 24 h; the 6th `POST
  /interviews` → `DAILY_INTERVIEW_LIMIT` (`429`).
- **Kill switch.** `AI_ENABLED=false` disables all external calls; the app runs in stub mode
  (canned schema-valid content via `StubAiClient`, §5.5). This is **not** an error at the
  trust boundary — the interview proceeds. The `ai` module still records an `llm_calls` row
  (`cost_usd = 0`) so the audit stays whole, and logs `AI_DISABLED_STUB_MODE`.
- Voice path (time ceiling + reconciliation) is `voice`/`worker`; not enforced here.

### 6. `cut_short` (K5)

The interview may end early (`ended_reason = 'cut_short'`) but is **never extended** past N.
The MVP trigger is **2 consecutive empty/blank answers** (batch generation has no per-answer
scoring — that is K4); once K4 lands, **2 consecutive answers scored `overall ≤ 1`** is added
as a second trigger. On either, backend performs the transition `hr_round | tech_round →
evaluating` and enqueues the report exactly as for a normal end.

### 7. Pause / resume (§8.3, K2)

A provider timeout/error during a generation or scoring call transitions the interview to
`paused` (no data loss, resumable). `POST /interviews/:id/resume` returns it to the active
round once `/readyz` dependencies are back. Every external call has a bounded timeout, a
retry with backoff and no unbounded wait (§8.3); exhausted retries on a *live* call →
`paused`, on the *report* job → `failed` (K10).

### 8. Auth behaviour (K8, K8.5)

- **Register:** password **≥ 10 characters**, no other composition rule → `PASSWORD_TOO_SHORT`
  (`422`) otherwise. Email stored lowercased and unique → duplicate is `EMAIL_TAKEN` (`409`).
  On success the session is issued immediately **and** a `verify` token is minted with an
  `email.send` job enqueued (K8.6) — registration never waits on SMTP and never blocks on the
  mail being read.
- **Login:** verify argon2id (`@node-rs/argon2`). Wrong email or password →
  `INVALID_CREDENTIALS` (`401`), indistinguishable between the two.
- **Google (PKCE via `arctic`):** state/verifier validated → `OAUTH_STATE_MISMATCH` (`400`)
  on mismatch. Then:
  - Existing password account, Google `email_verified: true` → **link** and issue session.
  - Existing password account, `email_verified` not true → `ACCOUNT_LINK_REQUIRES_PASSWORD`
    (`403`), no session.
  - No existing account → create a `user` with `password_hash = null` and issue session.
- **Admin restriction (K8, brief-mandated negative requirement):** a `role = 'admin'`
  account may sign in **only** with email + password. Rejected with `ADMIN_MUST_USE_PASSWORD`
  (`403`) — checked **twice**: in the Google callback **and** at session creation. No session
  is created (`admin_auth.feature`).
- A `password_hash = null` (Google-only) account cannot be promoted to `admin` without first
  setting a password (K8.5) — otherwise the admin restriction would lock it out entirely. The
  supported way to set that first password is the K8.6 reset flow.

### 8a. Email verification and password reset (K8.6)

One table, two kinds: `email_tokens(user_id, kind ∈ {verify, reset}, token_hash, expires_at,
consumed_at)`.

- **Token generation:** 32 cryptographically random bytes, base64url-encoded for the link.
  **Only `sha256(token)` is stored**; lookup hashes the presented value and compares. A database
  dump therefore yields no usable link, and no log line can leak one (§7.2).
- **Single use:** a token with a non-null `consumed_at`, an `expires_at` in the past, or no row is
  answered identically — `EMAIL_TOKEN_INVALID` (`400`) for absent/consumed, `EMAIL_TOKEN_EXPIRED`
  (`400`) for expired. Consumption is a guarded update
  (`UPDATE … SET consumed_at = now() WHERE id = $id AND consumed_at IS NULL`); `count === 0` means
  another request won the race and the caller gets `EMAIL_TOKEN_INVALID`. Two clicks on the same
  link never verify twice.
- **TTL:** verify `EMAIL_VERIFY_TTL_HOURS` (default 24), reset `PASSWORD_RESET_TTL_MINUTES`
  (default 60).
- **Verification confirm** sets `users.email_verified_at`; already-verified is idempotent (`200`).
- **Resend cooldown:** 60 s per user, tracked in Redis → `EMAIL_RESEND_COOLDOWN` (`429`) with the
  remaining seconds in the response body, plus the §10 rate limit.
- **Reset request never reveals account existence.** Always `202` with an empty body, whether the
  email exists, is Google-only, or is unknown. Only the enqueued job differs.
- **Reset confirm** re-hashes with argon2id, then **revokes every session of that user**
  (`sessions.revoked_at = now()`), including the caller's. It also sets `email_verified_at` if
  null — control of the mailbox was just proven. A Google-only account (`password_hash = null`)
  gains its first password this way.
- **Google sign-in with `email_verified: true`** sets `email_verified_at` if null (K8.6).
- **Enforcement is one gate, config-driven** (§11.3): when `EMAIL_VERIFICATION_REQUIRED=true`,
  `POST /interviews` requires a non-null `email_verified_at` → `EMAIL_NOT_VERIFIED` (`403`).
  **No other endpoint is gated**, and the flag ships `false` with seeded accounts pre-verified so
  `SETUP.md` never depends on reading an inbox (K8.6). The flag switches *configuration*, never a
  code path — the check exists in one place and reads the flag.
- **Mail is never sent inline.** Every send is an `email.send` BullMQ job (K10) carrying
  `{ userId, kind, token }`; `worker` renders and delivers it. The API's latency is unaffected by
  SMTP, and a mail outage degrades to a retried job instead of a failed registration.

### 8b. Account onboarding profile (K8.7, §3.3 layer 1)

- **`PATCH /me/profile` is per-card.** The body is `{ step: 1 | 2 | 3, fields }`, Zod-validated
  **per step** — card 1 `{ fullName?, jobTitle?, dateOfBirth? }`, card 2
  `{ education: [{ school, degree, field, graduationYear }] }` with **at most 5 rows**, card 3
  `{ hobbies: string[], interestsText? }`. Fields merge into `users.profile`; a card sent twice
  overwrites its own keys and touches no others.
- **Partial is valid.** No field is required. `POST /me/profile/complete` sets
  `onboarding_completed_at` and is also the *skip* path — a skipped profile is data, not an error.
- **CV:** `POST /uploads` with `kind = 'cv'` stores the object (private, K12), sets
  `users.cv_upload_id`, and writes the extracted text to `users.profile.cv_text`, truncated to
  **12 000 characters** with `LISTING_TRUNCATED`-style logging (`CV_TRUNCATED`). A new CV replaces
  the pointer; the previous object stays in the bucket (content-addressed, deduplicated by
  `sha256`).
- **The merge happens server-side, once, at `POST /interviews/:id/profile`** (§3.3):
  `candidate_profile = { account: <users.profile minus dateOfBirth>, cvText?, perInterview }`.
  A **snapshot**, so editing a profile in March cannot change what a January report was reasoned
  from. The client never assembles it.
- **`date_of_birth` is stripped before the value leaves the database boundary toward `ai`** and is
  excluded from every log line (§3.3, §7.2). Age is not an interview input.

### 9. Upload validation (§7.2, K12)

`POST /uploads`: **≤ 10 MB** (`UPLOAD_TOO_LARGE`, `413`); MIME **and** magic-bytes must be
PDF (`UNSUPPORTED_MEDIA_TYPE`, `415`); **≤ 30 pages** (`UPLOAD_TOO_MANY_PAGES`, `422`); text
extracted with `unpdf` (no OCR). A scanned PDF yielding **< 200 characters** →
`PDF_TEXT_TOO_SHORT` (`422`), asking the candidate to paste instead (US-04). Deduplicated by
`sha256` at the db layer (K12) — a re-upload reuses the row, not an error.

`kind` is required and validated (`listing` | `cv`); the limits above are identical for both. The
only difference is what the row is attached to: a `listing` upload is referenced by an interview,
a `cv` upload is referenced by `users.cv_upload_id` and its text cached on the profile (§8b).
Both classes are **private** objects reached only by a 5-minute signed URL (K12) — a CV is the most
personal document a user gives us and is never public-read.

**There is no URL-fetch intake.** Listings arrive as pasted text or an uploaded PDF only; server-
side fetching of a user-supplied URL was considered and cut (§4.3.1) — it is an SSRF surface with
no scored requirement behind it. Any future reintroduction is a security-reviewed change, not a
convenience patch.

### 10. Rate limiting (§7.2, Redis)

| Action | Limit | Key | Code |
|---|---|---|---|
| sign-in | 5 / min | IP | `RATE_LIMITED` (`429`) |
| register | 3 / hour | IP | `RATE_LIMITED` (`429`) |
| interview start | 10 / hour | user | `RATE_LIMITED` (`429`) |
| verification resend | 5 / hour (+ 60 s cooldown) | user | `RATE_LIMITED` (`429`) / `EMAIL_RESEND_COOLDOWN` (`429`) |
| password-reset request | 5 / hour | IP | `RATE_LIMITED` (`429`) |
| profile card save | 60 / hour | user | `RATE_LIMITED` (`429`) |

The reset limit is keyed by IP rather than user because the endpoint must not distinguish existing
from unknown accounts (K8.6) — a per-user key would leak existence through the limit itself.

### 11. Prompt-injection boundary (§7.1)

Backend passes attacker-controlled listing text to `ai` as *data*, never merged into a
system prompt. Neutralisation, the `<job_listing>` block, the 12 000-character truncation
(`LISTING_TRUNCATED`) and the `SECURITY_PROMPT_INJECTION_SUSPECTED` log are enforced in the
`ai` `PromptBuilder` (asserted directly, §5.5) — not here. Backend's obligation is to route
the raw listing to `ai` unmodified and never to interpolate it into any control path.

## Failure modes

Every row is a Stage-2 scenario candidate. Codes are stable `SCREAMING_SNAKE_CASE` (§4.5);
none is a display string. Codes marked † are inherited from the `db` spec's registry.

| Condition | Code | HTTP | Recovery |
|---|---|---|---|
| Register password < 10 chars | `PASSWORD_TOO_SHORT` | 422 | Choose a longer password |
| Register duplicate email | `EMAIL_TAKEN` † | 409 | Sign in or use another email |
| Login wrong email/password | `INVALID_CREDENTIALS` | 401 | Re-enter credentials |
| Admin uses Google (callback or session creation) | `ADMIN_MUST_USE_PASSWORD` | 403 | Sign in with email + password |
| Google links to an unverified-email account | `ACCOUNT_LINK_REQUIRES_PASSWORD` | 403 | Sign in with the password first |
| OAuth state/verifier mismatch | `OAUTH_STATE_MISMATCH` | 400 | Restart sign-in |
| Any authed route without a valid session | `UNAUTHENTICATED` | 401 | Sign in |
| Non-admin hits `/admin/*` | `FORBIDDEN` | 403 | — |
| `:id` not owned by the user (or absent) | `INTERVIEW_NOT_FOUND` | 404 | — |
| Out-of-turn / stale answer | `QUESTION_NOT_CURRENT` † | 409 | Refetch `GET /interviews/:id/state`, retry |
| Transition absent from K2's table | `INVALID_STATE_TRANSITION` † | 409 | Resync from state |
| Pre-call budget check shows `spent_usd ≥ budget_usd` | `BUDGET_EXCEEDED` † | 402 | Interview → `evaluating` (`budget_exhausted`); read the report |
| 6th interview in 24 h | `DAILY_INTERVIEW_LIMIT` | 429 | Wait until the window rolls |
| Rate-limit tripped | `RATE_LIMITED` | 429 | Retry after the window |
| Upload > 10 MB | `UPLOAD_TOO_LARGE` | 413 | Upload a smaller file |
| Upload not a PDF (MIME or magic bytes) | `UNSUPPORTED_MEDIA_TYPE` | 415 | Upload a PDF |
| Upload > 30 pages | `UPLOAD_TOO_MANY_PAGES` | 422 | Trim the file |
| Extracted PDF text < 200 chars | `PDF_TEXT_TOO_SHORT` | 422 | Paste the listing text |
| Setup with neither `jobText` nor `uploadId` | `LISTING_REQUIRED` | 422 | Provide a listing |
| `POST /interviews` while unverified and `EMAIL_VERIFICATION_REQUIRED=true` | `EMAIL_NOT_VERIFIED` | 403 | Verify from `/verify-email`; the typed listing is preserved client-side |
| Verify/reset token absent or already consumed | `EMAIL_TOKEN_INVALID` | 400 | Request a new link |
| Verify/reset token past `expires_at` | `EMAIL_TOKEN_EXPIRED` | 400 | Request a new link |
| Resend requested inside the 60 s cooldown | `EMAIL_RESEND_COOLDOWN` | 429 | Wait the returned seconds |
| Profile card body fails its per-step schema (incl. > 5 education rows) | `VALIDATION_ERROR` | 422 | Correct the card |
| `POST /uploads` with an unknown or missing `kind` | `VALIDATION_ERROR` | 422 | Send `listing` or `cv` |
| Body fails Zod at any boundary | `VALIDATION_ERROR` | 422 | Correct the request |
| State-changing request, `Origin`/`Referer` ≠ `PUBLIC_ORIGIN` | `CSRF_ORIGIN_MISMATCH` | 403 | — |
| `/readyz` and a dependency is down | `NOT_READY` | 503 | Wait; do not route traffic |

## Observability

Every log line is `logger.<level>({structured}, "EVENT_NAME")` carrying **both** `traceId`
(per-request) and `interviewId` where an interview is in scope (K6). Free-form sentences are
banned; no passwords, tokens, keys, PII or PDF content. Mandatory events this area emits:

- **Request:** `HTTP_REQUEST` on every request (method, path, status, latency).
- **Auth:** `AUTH_REGISTERED`, `AUTH_LOGIN_OK`, `AUTH_LOGIN_FAILED`, `AUTH_GOOGLE_LINKED`,
  `AUTH_ADMIN_GOOGLE_BLOCKED`, `AUTH_LOGOUT`.
- **Account lifecycle (K8.6):** `AUTH_VERIFY_TOKEN_ISSUED`, `AUTH_EMAIL_VERIFIED`,
  `AUTH_VERIFY_TOKEN_REJECTED` (with a `reason` of `invalid|expired|consumed`),
  `AUTH_RESET_TOKEN_ISSUED`, `AUTH_RESET_COMPLETED` (with the count of sessions revoked),
  `AUTH_VERIFICATION_REQUIRED_BLOCK`. **No log line contains a token, a token hash or the email
  body** — `userId` is the only identifier written.
- **Profile (K8.7):** `PROFILE_CARD_SAVED` (step only), `ONBOARDING_COMPLETED`, `CV_UPLOADED`
  (`uploadId`, size, page count), `CV_TRUNCATED`. **Never** the CV text, a profile field value, or
  `date_of_birth` — the event says a card was saved, not what was in it (§7.2).
- **State machine:** `INTERVIEW_STATE_CHANGED` (from, to, endedReason) on every transition.
- **Flow:** `HR_BATCH_REQUESTED`, `TECH_BATCH_REQUESTED`, `ANSWER_RECORDED`,
  `LANGUAGE_SWITCHED` (from, to), `INTERVIEW_CUT_SHORT`.
- **Cost/security trips:** `BUDGET_EXHAUSTED`, `DAILY_LIMIT_HIT`, `RATE_LIMIT_HIT`,
  `AI_DISABLED_STUB_MODE`. (`SECURITY_PROMPT_INJECTION_SUSPECTED` and `LISTING_TRUNCATED` are
  emitted by `ai`, cited here for the admin panel in US-29.)
- **Queue boundary:** `REPORT_JOB_ENQUEUED` (worker emits the job-run events).

An admin debugging a bad report searches by `interviewId`, then follows `traceId` per
request, then the `(prompt_uuid, prompt_version)` on `llm_calls` (K9) — answerable from
Kibana **or** `docker compose logs api | grep <interviewId>` when Kibana is down (§15.2
story 16).

## Security

Backend sits on the primary request trust boundary — every browser request and every
server-to-server webhook crosses it here.

- **Authentication** is a DB-backed opaque session cookie (`httpOnly`, `Secure`,
  `SameSite=Lax`), server-revocable (K8). No token or hash is ever logged or returned.
- **Authorisation** is an ownership check on every `:id` route and a `role = 'admin'` check
  on every `/admin/*` route (§7.2). A non-owned resource is `INTERVIEW_NOT_FOUND` (existence
  not leaked), not `FORBIDDEN`.
- **CSRF** — `SameSite=Lax` plus an `Origin`/`Referer` check on every state-changing request
  (`CSRF_ORIGIN_MISMATCH`).
- **Input validation** — Zod at every trust boundary; upload validated by size, MIME **and**
  magic bytes before a byte is stored (§7.2, K12).
- **Prompt injection** — the listing crosses to `ai` as data only; backend never interpolates
  it into a control path (§7.1; the defence is asserted in `ai`).
- **Rate limits** on sign-in, register, interview start, verification resend, reset request and
  profile saves (§7.2) blunt credential-stuffing, mail-bombing and cost abuse.
- **Account-recovery tokens** are 32 random bytes stored only as `sha256`, single-use through a
  guarded update, short-TTL, and never logged or echoed (K8.6). A completed reset **revokes every
  session**, which is the whole point of the button.
- **No account enumeration** on `POST /auth/password-reset/request` — identical `202` for every
  input, and an IP-keyed rate limit so the limiter cannot leak existence either.
- **PII discipline on the profile** (§3.3): `date_of_birth` never reaches `ai` and never reaches a
  log; CV text is truncated, neutralised as untrusted input (§7.1) and stored server-side only; the
  CV object is private with 5-minute signed URLs (K12).
- **No user-supplied URL is ever fetched server-side** (§9, §4.3.1) — the SSRF surface does not
  exist rather than being defended.
- **Secrets** are env-only; `.env.example` carries fakes (§7.2). `AI_ENABLED=false` is the
  global kill switch (§7.3).
- **Webhook auth** (HMAC + timestamp window) is `voice`/§3.5; backend only forwards
  `/webhooks/*` and asserts nothing about it here.

## Open questions

Empty. The three forks this spec raised were resolved during authoring and are recorded below
so every downstream claim is traceable. None is a new requirement.

1. **`cut_short` trigger (K5).** MVP = **2 consecutive empty/blank answers** → `cut_short`
   (no per-answer scoring exists pre-K4); when K4 lands, **2 consecutive answers scored
   `overall ≤ 1`** is added. Backend performs `hr_round | tech_round → evaluating` either way.
2. **Language-detection thresholds (§3.4).** `detectLanguage` (owned by `ai`) returns the other
   language when a **non-Latin Unicode script ratio > 0.6**, else when a **stop-word hit ratio
   ≥ 0.15** against that language's list; below both it is *ambiguous* and keeps
   `interviews.language`. The thresholds and turn unit (one answer; two consecutive to switch)
   are fixed here; the **stop-word list contents and the supported-language set are `ai`'s to
   enumerate** (ai Q1) and do not gate backend behaviour, which only consumes
   `{ language, ambiguous }`.
3. **`ended_reason` on a K10 report failure.** `ended_reason` keeps whatever entered
   `evaluating` (usually `completed`); `state = 'failed'` carries the report-job failure, which
   admin surfaces with the job's dead-letter cause. No new `EndedReason` value.

## Acceptance criteria

Each is observable from outside the code — an HTTP call, a status/error code, or a state
read. Every criterion maps to at least one Stage-2 Gherkin scenario.

1. `POST /auth/register` with a password of 9 characters returns `422 PASSWORD_TOO_SHORT`
   and creates no `user`; with ≥ 10 characters it returns `201`, sets the session cookie, and
   `GET /me` then returns the user.
2. Registering an email that already exists (case-insensitively) returns `409 EMAIL_TAKEN`.
3. `POST /auth/login` with a wrong password returns `401 INVALID_CREDENTIALS`; a correct one
   returns `200` and a working session cookie.
4. A `role = 'admin'` account completing Google sign-in is rejected with
   `403 ADMIN_MUST_USE_PASSWORD` and **no session is created**; the same account signs in with
   email + password successfully.
5. Google sign-in for an email that owns a password account links only when
   `email_verified` is true; otherwise it returns `403 ACCOUNT_LINK_REQUIRES_PASSWORD`.
6. `POST /interviews` with 8 questions returns `hrQuestionCount = 3` and `techQuestionCount
   = 5`, and moves the interview to `profiling`.
7. After `POST /interviews/:id/profile`, exactly `hrQuestionCount` HR `questions` rows exist
   ordered 1..hr, the state is `hr_round`, and the technical round has no questions yet.
8. Submitting an answer for a question that is not at `current_index` returns
   `409 QUESTION_NOT_CURRENT` and leaves `current_index` unchanged.
9. `GET /interviews/:id/state` after 3 of 8 answers returns `currentIndex = 4` and a
   transcript cursor covering the 3 answers; the same call serves resume-after-refresh.
10. An answer submission records `answers.duration_ms` = `answered_at − deliveredAt`, server
    set, with no audio involved.
11. When the pre-call budget check reads `spent_usd ≥ budget_usd` in-transaction, no `ai`
    call is made, the interview moves to `evaluating` with `ended_reason = 'budget_exhausted'`,
    the submitted answer is preserved, and the request returns `402 BUDGET_EXCEEDED`.
12. The 6th `POST /interviews` by one user within 24 h returns `429 DAILY_INTERVIEW_LIMIT`.
13. Sign-in beyond 5/min/IP, register beyond 3/hour/IP and interview-start beyond
    10/hour/user each return `429 RATE_LIMITED`.
14. `POST /uploads` rejects a > 10 MB file (`413`), a non-PDF by magic bytes (`415`), a
    > 30-page PDF (`422`), and a PDF whose extracted text is < 200 characters
    (`422 PDF_TEXT_TOO_SHORT`); a valid PDF returns `201` with an `uploadId`.
15. A state-changing request whose `Origin` differs from `PUBLIC_ORIGIN` returns
    `403 CSRF_ORIGIN_MISMATCH`.
16. Every transition not in K2's table returns `409 INVALID_STATE_TRANSITION` with no state
    change; every listed transition succeeds and emits `INTERVIEW_STATE_CHANGED` with `from`,
    `to` and `interviewId`.
17. `DELETE /interviews/:id` returns `204`, and the interview disappears from
    `GET /me/interviews` while remaining visible in `GET /admin/interviews` with `deleted:
    true` and its cost intact.
18. `GET /admin/interviews` requires an admin session (`403 FORBIDDEN` otherwise) and lists
    deleted interviews; `GET /admin/stats` returns the K11 metrics computed to their fixed
    definitions.
19. `GET /readyz` returns `503 NOT_READY` when Postgres or Redis is unreachable and `200`
    when both are up; `GET /healthz` returns `200` while the process is alive.
20. Entering `evaluating` enqueues exactly one report job (idempotent by `interviewId`) and
    emits an SSE nudge on `GET /events/interviews/:id`; the report is served by
    `GET /interviews/:id` once ready.
21. `POST /auth/register` enqueues exactly one `email.send` job of kind `verify` and returns
    without waiting on SMTP; `GET /me` then reports `emailVerifiedAt = null`.
22. `POST /auth/verify-email/confirm` with a valid token sets `email_verified_at` and returns
    `200`; **submitting the same token again returns `400 EMAIL_TOKEN_INVALID`** and does not
    change the user; a token past its TTL returns `400 EMAIL_TOKEN_EXPIRED`.
23. Two concurrent confirms of the same token result in exactly one success and one
    `EMAIL_TOKEN_INVALID` (guarded `consumed_at` update).
24. A second `POST /auth/verify-email/request` inside 60 s returns `429 EMAIL_RESEND_COOLDOWN`
    with the remaining seconds; beyond 5 requests in an hour it returns `429 RATE_LIMITED`.
25. `POST /auth/password-reset/request` returns `202` with a byte-identical body for a registered
    email, a Google-only account and an unknown address; only the enqueued job differs.
26. `POST /auth/password-reset/confirm` with a valid token and a ≥ 10-character password succeeds,
    and **every** session of that user is revoked — a request with the pre-reset cookie then
    returns `401 UNAUTHENTICATED`. A 9-character password returns `422 PASSWORD_TOO_SHORT` and
    leaves the token unconsumed.
27. A Google-only account (`password_hash = null`) can set its first password through the reset
    flow, after which email+password sign-in works.
28. No token, token hash or mail body appears in any log line emitted by the flows above
    (asserted against the in-memory `LogSink`, §5.5).
29. With `EMAIL_VERIFICATION_REQUIRED=true`, `POST /interviews` from an unverified user returns
    `403 EMAIL_NOT_VERIFIED` and creates no interview; with the flag `false` the same request
    succeeds. **No other endpoint changes behaviour with the flag.**
30. `PATCH /me/profile` with card 1 fields persists them and leaves cards 2–3 untouched;
    re-sending card 1 overwrites only its own keys. A card-2 body with 6 education rows returns
    `422 VALIDATION_ERROR`.
31. `POST /me/profile/complete` sets `onboarding_completed_at`, and `GET /me` then reports it;
    a profile with unset fields is returned as partial data with no error.
32. `POST /uploads` with `kind = 'cv'` returns `201`, sets `users.cv_upload_id`, populates
    `users.profile.cv_text` (truncated at 12 000 characters, logging `CV_TRUNCATED`), and the
    stored object is **not** publicly readable — only a signed URL retrieves it.
33. `POST /interviews/:id/profile` writes `candidate_profile` as
    `{ account, cvText?, perInterview }` where `account` **contains no `dateOfBirth` key**, and the
    generation request that follows contains no date of birth anywhere in its payload.
34. Editing `users.profile` after an interview reached `hr_round` does not change that interview's
    `candidate_profile` (snapshot, not reference).
35. `GET /me` returns `onboardingCompletedAt`, `emailVerifiedAt` and `interviewCount`, which is all
    a client needs for first-run routing (K8.7); no endpoint exists that fetches a listing from a
    user-supplied URL.
