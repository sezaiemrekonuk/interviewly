# platform — spec

**Date:** 2026-08-12
**Status:** draft
**Derives from:** IDEA.md §11 (deployment and CI/CD), §15 (out of scope), `2026-07-29-infra.md`
**Reverses:** IDEA.md §11's "no Kubernetes, no Helm", "load balancers, multi-instance and
autoscaling are **not built**", and §11.5's cut image registry. See ADR-P01.
**Related:** `2026-07-29-infra.md` (owns compose, CI and the single-VM shape it replaces)

## Scope

The system runs on one VM under `docker compose`, behind Caddy on port 80, and no claim has ever
been made about what it holds. This ledger deploys it twice — to Fly.io as the live target and to
a local `kind` cluster as the orchestrated one — drives both with synthetic traffic, and writes
down what each replica count actually buys.

The traffic is fake. The routing is not: real replicas, real load balancers, real horizontal
pod/machine scaling. A number produced against one process behind a proxy that never balances
anything is not a scale level, and this ledger's whole output is the number.

Owns: the image registry, the Fly topology and its managed dependency swaps, the Kubernetes
manifests, the load-test provider profile, the k6 scenarios, and `SCALE.md`.

Does not own: the SSE connection ceiling it will measure and name (§8), KEDA, multi-region,
Helm, Terraform, or any change to what the application does.

## Why this reverses a recorded decision

IDEA.md §11 rejected all of this for a reason that was correct at the time — a four-service demo
on one VM does not need an orchestrator, and building one is deployment cost with no scale
benefit. That reasoning is untouched for *production*. What changed is the question being asked:
not "what does this need to run" but "what does this hold, and where does it stop". Those have
different answers, and only the second one requires more than one replica to exist.

So §11 is superseded the way ADR-S01 superseded the voice ledger: the old text stands, the new
ADR says what changed and why, and nothing already `done` is reopened.

## The finding that decides what the doc says

`sse.ts` opens **one Redis connection per open stream**:

- [`backend/modules/interview/sse.ts:87`](../../backend/modules/interview/sse.ts) —
  `publishStateChanged` publishes to `redis.publish(eventChannel(...))`. Cross-replica fan-out
  already works; a state change on replica B reaches a stream held on replica A.
- [`backend/modules/interview/sse.ts:180`](../../backend/modules/interview/sse.ts) — every open
  stream calls `redis.duplicate()`. The comment at :212 says why, and names the alternative it
  deliberately did not build: "one shared subscriber would need an in-process channel → response
  map plus refcounted unsubscribe."

The consequence for this ledger: **concurrent live interviews scale 1:1 with Redis connections,
not with api replicas.** Adding api machines moves the CPU ceiling and does nothing to the
connection ceiling. Managed Redis (Upstash, which is what Fly offers) caps connections per plan,
and that cap is reached long before four api machines are busy.

This is measured and named, not fixed. The fix is a real task with a real risk — the refcounted
map the comment describes is where SSE fan-out bugs live — and it is not worth doing before there
is a number saying how much it buys. `SCALE.md` states the ceiling as the headline rather than
publishing a replica-count table that implies a knob which is not the binding one.

The worker side is already safe: [`worker/src/index.ts:87`](../../worker/src/index.ts) schedules
the abandon sweep through a BullMQ `JobScheduler`, whose state lives in Redis, so N worker
replicas produce one sweep per interval rather than N.

## Architecture

### 1. Registry — GHCR, three images, tagged by sha

`.github/workflows/images.yml` builds `backend/Dockerfile`, `worker/Dockerfile` and
`frontend/Dockerfile` on pushes to `master` and pushes to `ghcr.io/obss-ai-summer-internship-2026/interviewly-{api,worker,web}`
tagged with the commit sha. Fly deploys `--image`; `kind` side-loads the same digest with
`kind load docker-image`, so the cluster needs no registry credentials.

Reinstates what IDEA.md §11.5 cut. The reason it was cut — no deploy target — no longer holds,
and two targets consuming different images is how "it worked on Fly" becomes unfalsifiable.

**`NEXT_PUBLIC_*` are build args, not runtime env.** `compose.yaml`'s `web.build.args` block
already documents this and fails loudly when they are missing; the workflow inherits the same
obligation, and a `fly secrets set NEXT_PUBLIC_ASSETS_PREFIX` arrives far too late to matter.

### 2. Fly — four apps

`interviewly-edge`, `interviewly-web`, `interviewly-api`, `interviewly-worker`. Separate Fly apps
rather than process groups of one: the worker has no ports, scales on a different signal, and
sharing a scale count with the api would tie report throughput to HTTP concurrency.

**Caddy survives as `interviewly-edge`.** The existing `Caddyfile` moves across with upstreams
rewritten to `.internal` DNS and nothing else changed. It carries four behaviours that are not
free to re-derive:

- `handle_path /api/*` — prefix strip, without which every backend route 404s.
- `flush_interval -1` on the api upstream — the SSE no-buffering guarantee.
- `handle_path /assets/*` — the bucket-name rewrite that MinIO needed and Tigris needs too.
- the `Vary: Cookie, Accept-Language` header on negotiated paths, excluded from `_next/static`.

The alternative — Fly `[[services]]` per app plus Next rewrites — splits four rules across three
files and two systems. One extra internal hop is the cheaper trade, and it keeps the routing
truth in the file the repo already reviews.

Managed dependency swaps, all protocol-compatible so no application code changes:

| compose service | Fly | note |
|---|---|---|
| `db` | Fly Postgres | single node; not HA, and `SCALE.md` says so |
| `cache` | Upstash Redis | **the connection cap that §8 measures against** |
| `bucket` (MinIO) | Tigris | S3 API; `S3_ENDPOINT`/`S3_ACCESS_KEY`/`S3_SECRET_KEY` repoint |
| `mail` (Mailpit) | Resend or any SMTP | `SMTP_*` repoint; a sink is mandatory, not optional — registration always enqueues a mail |
| `migrate` | `[deploy] release_command` on api | runs once, exits before the new version serves |

Two more carried obligations:

- **`kill_timeout = 15` on the api app.** `compose.yaml` sets `stop_grace_period: 15s` above the
  API's own 10s drain ceiling for issue #70. Fly's default kill timeout is 5s, which SIGKILLs a
  machine mid-answer.
- **`REDIS_URL` must not resolve to db 0 for anything that flushes.** Not a production concern,
  but the load-test profile inherits the acceptance suite's habits; see §5.

Scale surface: `fly scale count api=N`, `min_machines_running`, and
`auto_stop_machines = 'suspend'` so idle cost stays near zero between measurement runs.

### 3. Kubernetes — kind, kustomize, no cloud bill

`k8s/base/` (Deployments `web`/`api`/`worker`, Services, Ingress, ConfigMap, Secret, a `migrate`
Job with `ttlSecondsAfterFinished`, HPA on api) and `k8s/overlays/kind/` (in-cluster `db`, `cache`,
`bucket` as single-replica Deployments with PVCs, plus NodePort wiring).

Kustomize, not Helm: two overlays and no chart consumers. Deployments with PVCs, not StatefulSets:
nothing here clusters, and a kind cluster is deleted at the end of the session.

Probes reuse endpoints that already exist and currently have exactly one caller each — the
compose healthchecks:

| workload | probe | source |
|---|---|---|
| api | `GET :4000/healthz` | `compose.yaml` api healthcheck |
| worker | `GET :${WORKER_HEALTH_PORT:-4100}/healthz` | `worker/src/health.ts`, issue 71 |
| web | `GET :3000` | `compose.yaml` web healthcheck |

**ingress-nginx buffers responses by default, and that stalls every SSE stream.** The manifests
must set `nginx.ingress.kubernetes.io/proxy-buffering: "off"` and a `proxy-read-timeout` longer
than an interview. This is the exact mirror of Caddy's `flush_interval -1`, and it is the single
most likely reason a k8s deploy of this app looks broken while every pod reports Ready.

**HPA goes on api only.** The worker is LLM-bound: it sits at near-zero CPU while waiting on a
provider, so a CPU-target HPA scales it down under exactly the load it should scale up for. The
worker stays at a fixed replica count and `SCALE.md` states the reason. Queue-depth autoscaling is
KEDA's job and is out of scope — naming it here so the omission reads as a decision.

### 4. Routing is real, traffic is fake

Nothing about the request path is simulated. Fly Proxy balances across api machines; ingress-nginx
balances across api pods; both terminate real connections and both are where the numbers come
from. What is synthetic is who is calling and what the providers say back.

### 5. The load-test provider profile

Half of it exists. `AI_ENABLED=false` already selects `StubAiClient` through
[`packages/ai/src/resolve-client.ts:38`](../../packages/ai/src/resolve-client.ts), and stub mode
still writes audit rows (`StubRecordingClient`), so cost accounting stays exercised.

The other half does not. `FakeSpeechProvider` exists at
[`backend/modules/speech/fake-speech.ts`](../../backend/modules/speech/fake-speech.ts) but is
referenced **only** from `features/step_definitions/` and `speech.test.ts`. The seam itself is
already there — `setSpeechProvider` at
[`backend/modules/speech/SpeechProvider.ts:27`](../../backend/modules/speech/SpeechProvider.ts)
swaps the module-level binding wholesale, and the acceptance ring calls it from a `Before` hook.
What is missing is a **boot-time** caller: nothing outside tests ever swaps the binding, so a
deployed process always holds `ElevenLabsSpeech` and TTS/STT would bill for real at every scale
level. This ledger adds that one call, behind an env switch, alongside the `AI_ENABLED` switch that
already exists.

**Both stubs return instantly, and that is a measurement bug, not a convenience.** A live-interview
VU that gets its turn back in microseconds cycles through the loop with no think time, so an
instant-stub run reports a concurrency the real system will never see — the streams that matter
are the ones held open for seconds. The profile must inject fixed latency drawn from
`speech-latency/REFERENCE.md`'s measured warm medians (STT ~1 650 ms, conductor ~1 180 ms,
TTS ~430 ms since L01), so the load test's turn loop has the real system's shape with none of its
bill.

**The guard is the point.** A fake provider silently active in production is an interview that
scores nobody and looks fine. It gets the loudest available guard, modelled on the acceptance
suite's refusal to run against a database whose name does not end in `_test`: refuse to boot with
the fake speech provider selected unless the environment says so explicitly and `NODE_ENV` is not
production, and log the selection at startup either way.

### 6. k6 scenarios

`loadtest/http-browse.js` — anonymous landing, login, listing. Produces req/s and p95 against the
ordinary request path.

`loadtest/live-interview.js` — the one that matters. Each VU registers, creates an interview,
**holds the SSE stream open**, and submits answers on a timer for the interview's duration. The
concurrent-interviews figure is the VU count at which p95 turn latency crosses its threshold.

Ramping-VU executor, thresholds as `http_req_duration: p(95)<...`, JSON summary written to
`loadtest/results/{target}-{replicas}.json` so the tables in `SCALE.md` are transcribed from files
rather than from a terminal someone closed.

**Run the generator from a machine in the target region.** From a laptop the numbers measure a
home uplink, and the SSE scenario — thousands of long-lived connections from one host — will hit
local ephemeral-port and file-descriptor limits before it hits anything on the server.

Lowercase `k6` everywhere in prose and filenames. This repo already uses `K6`, `K9`, `K13` as
constraint ids from IDEA.md, and "K6" in a sentence about load testing is unreadable.

### 7. Baseline first

One replica under `docker compose`, measured before either deploy exists. Without it, a Fly number
has nothing to be compared against and every subsequent figure is an absolute with no meaning.

### 8. SCALE.md

`.agents/ledgers/platform/SCALE.md`, structured as:

1. **The ceiling, first.** Concurrent interviews bounded by Redis connections, with the
   `sse.ts:180` anchor and the measured connection count per stream. Stated before any table, so
   nobody reads the tables as a scaling promise.
2. **Two tables** — Fly and kind — of replicas × concurrent interviews × req/s × p95, transcribed
   from `loadtest/results/`.
3. **A physical deployment diagram** per target, mirrored into the root `DECISIONS.md`. That file
   landed on 2026-08-12 (`a973d56`) with a `## Physical deployment` section already drawing the
   compose topology in mermaid. The compose diagram stays; the two deployed ones join it, which is
   where IDEA.md §13's requirement stops being a diagram of an aspiration.
4. **What was faked and what was not.** Real routing, real replicas, real balancers; stubbed
   providers at fixed injected latency, with the latencies listed. A scale document that does not
   say what it stubbed is a marketing document.

## Out of scope

- **Fixing the SSE connection ceiling.** Measured and named by P09; the fix is its own task once
  there is a number justifying it.
- **KEDA / queue-depth autoscaling.** The correct tool for the worker, and a second control loop
  to debug for a demo that has none.
- **Multi-region, Helm, Terraform.**
- **Running the Cucumber suite against a cluster.** `tests/smoke/` gets a deployed-URL variant
  instead; the acceptance ring keeps running against compose, where it is fast and hermetic.
- **Any change to application behaviour.** If a scale finding requires one, it is a finding, and it
  goes in `SCALE.md` and a backlog row — not into a task in this ledger.

## Risks

- **Fly Postgres is a single node.** Fine for a demonstration, dishonest if unstated.
- **Money.** Machines, Postgres and Upstash all bill. `auto_stop_machines = 'suspend'` and
  tearing down between measurement runs are the mitigation; the cost of a scale run belongs in the
  devlog.
- **The `P` prefix touches a shared file.** `.agents/EXECUTE.md` §1 is the only authority on
  ownership and currently assigns infra (`F03`) to Sezai with no ledger owning deployment. Adding
  a `P` row and a tenth prefix needs the team's agreement before P01 starts, not after.
- **Two targets drift.** The same sha deployed to both is the only thing keeping them comparable;
  a hand-built kind image invalidates the comparison silently.
