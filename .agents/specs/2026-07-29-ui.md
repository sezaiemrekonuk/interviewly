## Scope

This spec pins the **design system and the avatar/mascot asset contracts** — the visual
vocabulary every screen is built from, not the screens themselves. It owns the visual direction
and per-surface density blend (§4.1 Cambly + Jotform), the complete design-token registry —
colour including the `--live` room state and the three-stop entry gradient, radius, the two
shadow tiers, typography (Outfit + Inter via `next/font`), type scale, spacing and motion
(§4.2) — the closed list of routes the gradient grounds, the accessibility floor every screen
must clear (§4.4), the `AvatarState` enum with its static-image asset pipeline, and the
`MascotPose` enum with its own pipeline and placement exclusions (§4.2.1): content-addressed
WebP keys, per-image and per-set size budgets, the public-read cache header, the preload
requirements, and the plain-`<img>` rendering rule (§3.6). It is the section `frontend` reads
to know which tokens, states and poses exist to compose with, and the section `db` reads to
mirror the enums and the `avatar_set` key shape.

**Not in this spec** (named owner):

- Route map, screen composition, room behaviour, the client avatar **state machine** (which
  state shows when), **which mascot pose a given screen renders and where it sits**, the SSE
  client, question widgets, admin charts, i18n message mapping — `frontend` (§4.3, §3.8, §3.9,
  K11, §4.5). This spec defines the tokens, the enums, the gradient's route list and the mascot
  exclusions; `frontend` composes screens with them.
- The `personas.avatar_set` **jsonb column** (`{ [AvatarState]: storageKey }`), the seed
  script that uploads defaults and writes keys, and the schema location of the enum — `db`
  (K13, §3.6). This spec fixes the enum's members and semantics and the key **layout**
  convention; `db` owns the column and the seed mechanics.
- `/assets/*` edge routing, public-read **enforcement** vs signed URLs, the storage bucket,
  and `next/font` self-hosting **mechanics** at the edge — `infra` (K12, K14, §7.4). This
  spec declares the cache header and the font families; `infra` makes them serve.
- The `AmplitudeAvatarDriver`, ElevenLabs audio wiring and any voice-room visual surface —
  `voice`, authored last (§12, §15.1). This spec fixes the enum both drivers share; the
  drivers themselves are elsewhere.
- The shared error-code registry file and locale message strings — foundations `F01`
  (§4.5, §5.2) and `frontend`. This spec authors no display strings and no error codes
  beyond the two asset-validation codes it defines below for `F01` to collect.

## Contracts

The concrete surface `ui` exposes. Everything here is a value or a name another area binds
to, not a screen.

### Design-token registry (§4.2)

Tokens are declared once as **CSS custom properties on `:root`** — the §4.2 names are
already `--`-prefixed, so the registry is their literal home. Any styling layer (plain CSS,
or Tailwind reading them through its theme — see Open questions) consumes these; no colour,
radius, shadow, font, size, spacing or motion value is written as a literal anywhere else.
**No CSS is authored before this registry lands** (foundations `F01`/F-a, §5.2, §4.2).

| Token | Value | Role |
|---|---|---|
| `--bg` | `#FBF9F6` | warm off-white ground — never pure white |
| `--surface` | `#FFFFFF` | raised surface |
| `--surface-sunken` | `#F4F2EE` | inset/sunken surface |
| `--text` | `#111436` | deep navy body text — never black |
| `--text-muted` | `#6B6F8D` | tinted muted text — never neutral grey |
| `--primary` | `#FF6100` | the single unmistakable action colour |
| `--primary-soft` | `#FFF1E8` | primary tint (backgrounds, hovers) |
| `--accent` | `#6F76F1` | informational only — never a CTA |
| `--live` | `#16A34A` | **interview-room live state only** — the `LIVE` badge and the active-speaker ring (§3.2). Never a CTA, never a success message |
| `--success` | `#10B981` | success |
| `--warning` | `#F59E0B` | warning |
| `--danger` | `#EF4444` | error/destructive |
| `--border` | `#E8E4DE` | hairline borders |
| `--grad-lavender` | `#EFE9FF` | gradient stop 1 |
| `--grad-cream` | `#FBF9F6` | gradient stop 2 (= `--bg`) |
| `--grad-peach` | `#FFE8D6` | gradient stop 3 |
| `--gradient-entry` | `linear-gradient(160deg, var(--grad-lavender) 0%, var(--grad-cream) 52%, var(--grad-peach) 100%)` | page ground of **entry surfaces only** — see Surface direction |

| Non-colour token | Value |
|---|---|
| Radius — panel / card / input / button | `24px` / `16px` / `12px` / `999px` |
| `--shadow-hairline` | `0 1px 2px rgba(17,20,54,0.06)` — the **only** shadow permitted inside the interview room |
| `--shadow-soft` | `0 8px 24px -12px rgba(17,20,54,0.12)` — entry surfaces and cards only |
| Heading font | **Outfit**, `next/font/google`, `display: swap`, weights **500 / 600 / 700** |
| Body & UI font | **Inter**, `next/font/google`, weights **400 / 500 / 600** |
| Type scale (px) | `13 / 14 / 16 / 20 / 28 / 40 / 56` — the only sizes (`56` is the landing/onboarding hero size) |
| Spacing | multiples of **4** |
| Motion | `150–250 ms ease-out`; **near-zero inside the interview room** |

**Fraunces is gone — recorded reversal (§4.2).** The direction is a bold geometric sans set
large, which is what both references actually use; the serif was carrying "warm" alone against
the grain of everything around it. **Outfit** replaces it for headings. **Inter stays for body
and UI** rather than setting one family throughout: Outfit at the 13–14 px steps reads
measurably worse, and keeping both costs one extra `next/font` call and no external request.

Fonts are **self-hosted through `next/font`** — no external font request, required by both
the LCP budget (§8.1) and the CSP (§7.4). `infra` owns the CSP/edge mechanics; this spec
fixes the families, weights and `display: swap`.

### Surface direction (§4.1)

The blend is a single warm-orange-over-neutrals family, applied at two densities:

| Surface | Direction | Density |
|---|---|---|
| Landing, auth, onboarding, setup, interview room, report | Cambly — warm, calm, face-first | Airy |
| Admin panel, forms, tables, dashboards | Jotform — structured, confident | Compact |

`--primary` is the only CTA colour on every surface; `--accent` is informational and is
**never** used for a call to action, at either density. `--live` is neither — it is a room
state (§3.2).

**Ground assignment is a closed list, not a judgement call.** `--gradient-entry` is the page
ground of exactly these routes — landing, register, sign-in, verification pending, forgot/reset
password, the three onboarding cards, setup, and pre-join. Every other surface — the interview
room, the report, history/dashboard and all of admin — uses flat `--bg`. A gradient behind a
live face is noise, and behind a data table it is worse. Cards **on** the gradient use
`--surface`; the gradient is never applied to a card.

| Shadow use | Allowed on |
|---|---|
| `--shadow-soft` | entry-surface panels and cards, option cards, the setup input container |
| `--shadow-hairline` | everything else, and the **only** shadow permitted in the interview room |

### Avatar state enum (§3.6)

The canonical enum. `db` mirrors these exact members as its `AvatarState` schema enum, and
`frontend` drives which one is shown (§3.8); both bind to this list.

```ts
type AvatarState = 'idle' | 'listening' | 'thinking' | 'speaking' | 'acknowledging'
```

| State | Shown when (semantics — the trigger mapping is `frontend`'s, §3.8) |
|---|---|
| `idle` | room mounted, nothing in flight |
| `listening` | the candidate is speaking / typing an answer |
| `thinking` | the interviewer is preparing the next question |
| `speaking` | the interviewer is delivering a question |
| `acknowledging` | brief beat immediately after an answer is received |

**Five states, five images minimum**, one image per state, per persona. A persona **may**
ship a second `speaking` variant — see Open questions; MVP does not.

### Avatar asset pipeline (§3.6)

The conventions the produced images and their storage keys obey. `db` writes these keys into
`avatar_set`; `infra` serves them; this spec fixes their shape.

- **Key layout:** `personas/{personaId}/{state}-{sha256}.webp` — content-addressed and
  therefore immutable, with no cache-invalidation problem.
- **Format & budget:** WebP, fixed dimensions, **~60 KB per image**, **~350 KB per persona
  set** (five images).
- **Access:** **public-read** — avatars are the only public objects; PDFs stay private with
  signed URLs (K12). Served with `Cache-Control: public, max-age=31536000, immutable`.
- **Preload:** the full set for **both** personas is fetched during the lobby/waiting
  screen, so the room opens with everything cached — no mid-interview pop-in.
- **Rendering:** plain `<img>` + `<link rel="preload">`, **not** `next/image` — routing
  static WebP through the Next loader against the in-Docker MinIO origin is configuration
  risk for zero gain.
- **Seeded:** `prisma/seed.ts` (`db`) uploads defaults and writes the keys; `docker compose
  up` + seed yields a working room with **no manual upload step**.

### Mascot pose enum and asset set (§4.2.1)

One illustrated character, five poses, shared across every entry surface. A **shared enum** for
the same reason `AvatarState` is one — the seed and the frontend both hardcode these as storage
keys.

```ts
type MascotPose = 'wave' | 'point' | 'think' | 'cheer' | 'shrug'
```

| Pose | Screens (placement is `frontend`'s; this is the semantic) |
|---|---|
| `wave` | landing hero, register, sign-in |
| `point` | setup screen (beside the input), onboarding card 1 |
| `think` | verification pending, onboarding card 2 |
| `cheer` | onboarding card 3, onboarding complete |
| `shrug` | empty states, error states |

- **Key layout:** `mascot/{pose}-{sha256}.webp` — content-addressed and immutable, same rule as
  avatars. **One shared set, not per-persona**, so there is no `{id}` segment.
- **Format & budget:** WebP, fixed dimensions, **~40 KB per image**, **~200 KB for the set**.
- **Access:** public-read, `Cache-Control: public, max-age=31536000, immutable` — the mascot
  joins avatars as the *only* public objects (K12).
- **Preload:** **only the poses the current screen uses**, not the set. Unlike avatars (§3.6),
  the mascot is never mid-interview, so there is no pop-in to prevent and preloading five images
  would spend LCP budget (§8.1) for nothing.
- **Placement rule (a hard exclusion, not a preference):** the mascot appears on **no** interview-
  room surface — the interviewer's face is the subject there — and on **no** admin surface
  (Jotform density, §4.1). A mascot rendered on either is a defect.
- **Rendering:** plain `<img>` + `<link rel="preload">`, same reasoning as avatars.
- **Seeded** by `prisma/seed.ts` alongside the avatar sets; keys are configuration, not user data.
- `alt` is developer-authored `next-intl` copy, never model output.

### Accessibility floor (§4.4)

The non-negotiable minimum every screen and component clears. `frontend` honours it per
screen; this spec is where it is fixed and where it is verified as a floor.

- Full **keyboard navigation**; a **visible focus ring** on every interactive element.
- **WCAG AA contrast** on all text/background token pairs (see Behaviour for the pinned
  pairs), **including each gradient stop individually** — an average is not a floor.
- `aria-live` on the live transcript / conversation panel, and on the **round handover**
  announcement so a screen-reader user learns that the other interviewer has taken over.
- `alt` on **every** image, including each avatar state and each mascot pose.
- `prefers-reduced-motion` respected — the §3.8 typing animation resolves **instantly**, and
  all token motion drops to near-zero, under it.
- **The setup input's glow is decoration, not a focus indicator.** It is present at rest, so
  focus is additionally indicated by the standard visible ring.
- **Active speaker is never colour-only.** The `--live` ring is always paired with the lit
  name/role label (and the `aria-live` handover above), so it survives colour blindness.

## Behaviour

Rules stated so two implementers produce the same result. Numbers, not adjectives.

1. **The token registry is the single source of colour, type, spacing, radius, shadow and
   motion.** A literal hex, px radius, shadow, font family, type size off the §4.2 scale, or
   spacing not a multiple of 4 appearing anywhere in the codebase is a defect. Type sizes are
   exactly the six on the scale; spacing values are exactly multiples of 4.

2. **`--primary` is the only CTA colour; `--accent` never is; `--live` is neither.** On any
   surface, the primary action uses `--primary` (or `--primary-soft` as its tint); informational
   emphasis uses `--accent`; `--live` is used **only** for the interview room's `LIVE` badge and
   active-speaker ring. Any of the three in another's role is a defect regardless of how it looks.

3. **Contrast pairs — AA is a hard floor (§4.4).** The following normal-text pairs must each
   meet WCAG AA (≥ 4.5:1); this is verified as a computed check, not judged by eye:
   `--text` on `--bg`, `--text` on `--surface`, `--text` on `--surface-sunken`,
   `--text-muted` on `--bg`, `--text-muted` on `--surface`, white text on `--primary`
   (the primary button label), white text on `--live` (the `LIVE` badge label), and
   **`--text` and `--text-muted` on each of `--grad-lavender`, `--grad-cream` and `--grad-peach`
   individually**. Any pair below 4.5:1 fails the floor.

4. **Motion is bounded and room-quiet.** Transitions are `150–250 ms ease-out`; inside the
   interview room motion is near-zero (§4.2). Under `prefers-reduced-motion`, all non-essential
   motion is removed and any content animation resolves to its end state instantly (§4.4) —
   including the setup input's glow and the active-speaker ring, which become static.

5. **Fonts load self-hosted with `display: swap`.** Outfit (500/600/700) for headings, Inter
   (400/500/600) for body and UI, both via `next/font/google`. No `@import` or `<link>` to an
   external font origin exists — the CSP forbids it (§7.4) and the LCP budget depends on it
   (§8.1). Fraunces appears nowhere.

5a. **The gradient's route list is closed.** `--gradient-entry` is the page ground of landing,
   register, sign-in, verification pending, forgot/reset password, the three onboarding cards,
   setup and pre-join — and of nothing else. The interview room, report, dashboard and admin use
   flat `--bg`. A gradient on a non-entry route, or applied to a card rather than the page ground,
   is a defect.

5b. **Shadow tier follows the surface.** `--shadow-soft` on entry-surface panels/cards only;
   everything else, and everything inside the interview room, is limited to `--shadow-hairline`.
   No other shadow value exists.

6. **Every persona carries all five avatar states** (§3.6). A persona whose `avatar_set` is
   missing any of the five enum keys is invalid — the seed must not produce one, and a
   validation check rejects it (`AVATAR_STATE_INCOMPLETE`, below). The optional second
   `speaking` variant is **not** part of MVP (Open questions §2).

7. **Avatar keys are content-addressed and immutable.** A key is
   `personas/{personaId}/{state}-{sha256}.webp` where `sha256` is the hash of the image
   bytes; the same bytes yield the same key, and changing an image yields a new key rather
   than mutating one. Objects are served `public, max-age=31536000, immutable`; a key that
   does not match its content hash is invalid (`AVATAR_KEY_MISMATCH`, below).

8. **The lobby preloads both personas' full sets** before the room opens (§3.6). Whether the
   preload has completed is observable (the `<link rel="preload">` set is present for all ten
   images); the room must not be the first place an avatar image is requested.

9. **Avatars and the mascot set are the only public-read objects.** No other stored object
   (listing PDFs, **CV PDFs**, reports) is public; those use signed URLs (K12, enforced by
   `infra`). This spec asserts the classification, not the enforcement.

10. **Every persona ships all five avatar states; the mascot ships all five poses.** A mascot set
    missing a pose is invalid (`MASCOT_POSE_INCOMPLETE`, below) on the same seed/CI check as
    `AVATAR_STATE_INCOMPLETE`, and mascot keys are content-addressed under the same
    `AVATAR_KEY_MISMATCH` rule (the check covers both prefixes).

11. **The mascot is excluded from the room and from admin** (§4.2.1). A mascot image rendered on
    any `/interviews/:id/room`, `/interviews/:id` report or `/admin/*` surface is a defect —
    stated as a rule so it is reviewable, not a matter of taste.

12. **Per-screen mascot preload only.** A screen emits `<link rel="preload">` for the pose(s) it
    renders and no others; a screen preloading the whole set fails the budget check (§8.1).

## Failure modes

`ui` is a token-and-asset contract, not an HTTP surface, so its failures are **build- and
seed-time validation** and **runtime graceful degradation** — not API error envelopes. The
two codes below are real validation failures surfaced by the seed/CI check; they are added to
the shared registry (`F01`, §4.5). Runtime degradations return no code (they are "not an
error").

| Condition | Code / signal | HTTP | Recovery |
|---|---|---|---|
| A persona's `avatar_set` is missing one of the five enum keys | `AVATAR_STATE_INCOMPLETE` | — (seed/CI fails) | Seed/CI aborts; the persona is fixed before merge — `docker compose up` must yield a complete set (§3.6, §10) |
| The seeded mascot set is missing one of the five poses | `MASCOT_POSE_INCOMPLETE` | — (seed/CI fails) | Seed/CI aborts naming the missing `pose`; fixed before merge (§4.2.1) |
| A stored avatar **or mascot** object's bytes do not hash to the `sha256` in its key | `AVATAR_KEY_MISMATCH` | — (seed/CI fails) | Re-upload; the content-addressed key is regenerated from the real bytes. One code covers both prefixes — the failure and the fix are identical |
| An avatar image fails to load at runtime | `<img>` `error` | — | *(not an error)* Fall back to the `idle` image, then a neutral placeholder; never a broken-image glyph, never a blank interviewer |
| A mascot image fails to load at runtime | `<img>` `error` | — | *(not an error)* The mascot is decoration: the slot collapses and the layout holds. Never a broken-image glyph, never a shifted form |
| A web font fails to load | `next/font` `swap` | — | *(not an error)* `display: swap` shows the fallback face; layout does not shift beyond the swap (§8.1) |
| A token is referenced that does not exist | build failure | — | Build/lint fails; there is no runtime "unknown token" state |

## Observability

`ui` emits **no** K6 runtime server logs — it is a static token and asset layer, not a
request path (K6 is a server contract, honoured by `backend`). Its debuggability lives at
**build and seed time**: the token-registry lint, the AA-contrast check, and the avatar-set
validation (`AVATAR_STATE_INCOMPLETE`, `AVATAR_KEY_MISMATCH`) each fail loudly in CI with the
offending token or `{ personaId, state }` named in the check output — never a free-form
sentence, and never image bytes or a persona system prompt in the log. An admin debugging a
missing avatar in a running room correlates via the `interviewId`/`personaId` the server
already logs (K6, `backend`); the asset layer adds nothing new to search by.

## Security

`ui` sits on one trust boundary — **the public-read avatar bucket** — and the classification
that boundary encodes:

- **Avatars and the mascot are public; nothing else is.** Those two seeded sets are the *only*
  public-read stored objects (§3.6, §4.2.1, K12); every other object — listing PDFs, **candidate
  CV PDFs**, generated reports — is private and reached by a signed URL. A CV made public-read
  would be the worst leak in the system: it is the most personal document a user gives us.
  Mis-classifying any object as public is a data-exposure defect. This spec fixes the
  classification; `infra` enforces it at the bucket/edge.
- **Content-addressed keys leak no identity.** Keys are `personas/{personaId}/{state}-{sha256}`
  and `mascot/{pose}-{sha256}` over seeded images — no user id, upload id, PII or token appears
  in either key or its public URL. Persona ids and poses are seed configuration (K13), not user
  data. Neither prefix is ever used for a user-supplied file.
- **`alt` text is developer-authored, never model output.** Avatar `alt` strings are static UI
  copy (`next-intl` keys, `frontend`), so the public image layer is not an injection surface;
  no LLM- or user-originated string is rendered as image metadata.
- **No external asset or font origin.** Self-hosted `next/font` and same-origin `/assets`
  mean the CSP stays `default-src 'self'` (§7.4, `infra`); this spec introduces no token,
  font or image dependency that would force the policy wider.

## Open questions

Each names who decides and what it blocks. This section must be empty before the spec is
marked `approved`.

1. **Styling-layer consumption of the token registry.** The tokens are fixed as `:root` CSS
   custom properties (§4.2), but whether components consume them through **plain CSS/CSS
   Modules** or through **Tailwind reading them via its theme** is not settled by IDEA.md.
   **Decides:** `frontend` + `ui` jointly, at the F-a CSS foundations task. **Blocks:** the
   shape of the F-a token file (a `:root` block vs a `tailwind.config` theme mapping) — **not**
   any token value, which is fixed here. **Recommended default:** declare the registry as a
   single `:root` custom-property block (the literal §4.2 names) and let whichever layer
   `frontend` picks read from it, so the values have exactly one home regardless of the layer.

2. **The optional second `speaking` avatar variant (§3.6).** §3.6 says a persona "may ship a
   second `speaking` variant", but `db`'s `avatar_set` is `{ [AvatarState]: storageKey }` —
   one key per state, with no slot for a second image on the same state. **Decides:** `db` +
   `ui`. **Blocks:** whether personas can ship the variant; blocks nothing in MVP.
   **Recommended default (taken):** MVP ships **exactly five keys**, one per state; the second
   `speaking` variant is deferred until `avatar_set` grows a per-state list. This keeps `db`'s
   current one-key-per-state shape and the ~350 KB set budget — YAGNI until a persona needs it.

3. **`AmplitudeAvatarDriver` feasibility (§3.6).** Whether the ElevenLabs web SDK exposes a
   `MediaStream`/`AudioNode` on the agent's TTS output — the input the amplitude driver needs —
   is unverified (§3.6, §15.1 item 3). **Decides:** `voice`, when it is authored (§12).
   **Blocks:** nothing in `ui` — the enum, the five images and the whole asset pipeline are
   driver-agnostic, and text mode uses the event driver regardless (`frontend`, §3.8). Noted
   here only because §3.6 raises it against the avatar; it is not a `ui` fork.

## Acceptance criteria

Each is observable from outside the code. **Verification surface note (§5.3):** Cucumber
drives the HTTP API, not a browser or a stylesheet, so these criteria are verified as
**build/seed checks** (token lint, computed AA-contrast assertion, avatar-set validation) and
a handful of **component/visual smokes** (React Testing Library / Playwright), **not** as
acceptance-ring Gherkin. They are still phrased as observable outcomes.

1. Every `--` token in §4.2 exists exactly once in the `:root` registry with the value in the
   table; a colour hex, radius, shadow, font family, off-scale type size, or non-multiple-of-4
   spacing value appearing as a literal outside the registry fails the token lint.
2. Each pinned contrast pair (`--text`/`--text-muted` over `--bg`/`--surface`/`--surface-sunken`
   and over **each of the three gradient stops**, white on `--primary`, white on `--live`)
   computes to **≥ 4.5:1**; a pair below 4.5:1 fails the AA-contrast check (§4.4).
3. The primary action element resolves to `--primary` (or `--primary-soft`); no element using
   `--accent` is a call to action; `--live` appears **only** on the room's `LIVE` badge and
   active-speaker ring (§4.1) — any other use of either is a defect.
4. Headings render in **Outfit** and body/UI in **Inter**, both loaded via `next/font` with
   `display: swap`; **Fraunces appears nowhere**; the built app makes **no** network request to
   an external font origin (§8.1, §7.4).
4a. `--gradient-entry` is the page ground on exactly the nine entry routes (landing, register,
   sign-in, verification pending, forgot password, reset password, onboarding × 3 as one route
   family, setup, pre-join) and on no other route; the room, report, dashboard and admin grounds
   compute to flat `--bg`.
4b. `--shadow-soft` appears only on entry-surface panels and cards; every element inside the
   interview room resolves to at most `--shadow-hairline`.
5. Under `prefers-reduced-motion`, all non-essential transitions are removed and any content
   animation resolves instantly to its end state (§4.4).
6. Every seeded persona's `avatar_set` contains all five `AvatarState` keys; a persona missing
   any key fails seed/CI with `AVATAR_STATE_INCOMPLETE` naming `{ personaId, state }` (§3.6).
7. Every avatar key matches `personas/{personaId}/{state}-{sha256}.webp` and the object's bytes
   hash to that `sha256`; a mismatch fails validation with `AVATAR_KEY_MISMATCH` (§3.6).
8. Avatar objects are served `Cache-Control: public, max-age=31536000, immutable` and are
   public-read; every non-avatar object (PDF, report) is **not** public and requires a signed
   URL (§3.6, K12).
9. Each avatar image is WebP, ~60 KB, and a full persona set is ~350 KB (five images); the
   budget is asserted against the seeded assets (§3.6).
10. The lobby emits a `<link rel="preload">` for all ten avatar images (both personas × five
    states) before the room route mounts, so the room requests no uncached avatar (§3.6).
11. Every rendered image, including each avatar state and each mascot pose, carries a non-empty
    developer-authored `alt`; every interactive element is keyboard-reachable and shows a visible
    focus ring — and on the setup input the ring is distinguishable from the at-rest glow (§4.4).
12. A running interview room whose avatar image fails to load shows the `idle` image or a
    neutral placeholder — never a broken-image glyph and never a blank interviewer (graceful
    degradation, §3.6). A failed mascot image collapses its slot with no layout shift.
13. The seeded mascot set contains all five `MascotPose` keys, each key matches
    `mascot/{pose}-{sha256}.webp` with bytes hashing to that `sha256`, each image is WebP at
    ~40 KB and the set is ~200 KB; a missing pose fails seed/CI with `MASCOT_POSE_INCOMPLETE`
    naming the pose, a bad hash with `AVATAR_KEY_MISMATCH` (§4.2.1).
14. Mascot objects are served `Cache-Control: public, max-age=31536000, immutable` and are
    public-read; **CV** and listing PDFs and reports are not public and require a signed URL
    (§4.2.1, K12).
15. No mascot image is rendered on any interview-room, report or `/admin/*` surface (§4.2.1).
16. A screen renders `<link rel="preload">` only for the mascot pose(s) it displays — a screen
    preloading the full set fails the check (§4.2.1, §8.1).
17. Under `prefers-reduced-motion` the setup input's glow and the active-speaker ring are static,
    and the active speaker remains identifiable without colour (lit name/role label plus the
    `aria-live` handover announcement) (§4.4).
